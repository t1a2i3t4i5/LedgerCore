# issue の書き方

雛形は [`.github/ISSUE_TEMPLATE/issue.md`](../.github/ISSUE_TEMPLATE/issue.md) にある。テンプレの HTML コメントには「何を書く枠か」だけを置き、**なぜそう書くのかはこちらにだけ**書く。

ここに挙げた節の多くは、**書き手が毎回思い出さないと消える** 性質を持つ。実際、この規約を作った時点で既存 29 件のうち「対象外」があるのは 2 件、「受け入れ条件」があるのは 10 件だけだった。枠として置いてあるのはそのためで、埋まっていない節があること自体は責めない。ただし「対象外」と「受け入れ条件」は残す（理由は各節の項に書く）。

## 節名は 7 つに寄せる

既存 issue は全 29 件が `##` 見出しで節分けされていた。骨格は最初からあったが、**同じ役割の節が別名で散っていた**。

| 役割 | 節名 | かつて使われていた別名 |
| --- | --- | --- |
| 状況の説明 | 事象 | 背景 / 問題 / 現状 / 前提 / 概要 / なぜ問題か / 何が起きるか |
| 変化の説明 | なぜ今これが問題になったか | （固定の別名なし） |
| 何をするか | 提案 | やること / 対応案 / 対応内容 / 実装 / ゴール |
| やらないこと | 対象外 | 含めないもの（必要なら別イシュー） |
| 検証 | テスト | 検証 / 実測での裏付け |
| 完了の判定 | 受け入れ条件 | 完了条件 |
| 参照 | 関連 | 関連 issue / 参考 |

「切り出しの理由」（`切り出した理由` / `なぜ PR #28 で対応しなかったか`）は独立した節にせず、**「関連」に畳んだ**。切り出し元の PR 番号と理由は必ず並ぶので、離すと片方だけ書かれる。

節名は既存の最頻値（「背景」22 回）ではなく、直近の #29 #30 #45 #49 で使われている語に寄せてある。最頻値は古い issue の蓄積で、今の書き方を代表していない。

## 事象 — 実測値とファイル:行 を添える

「〜が汚い」「〜が古い」で終わる指摘は、読む側が本当かどうかを自分で確かめ直すことになる。

[#29](https://github.com/t1a2i3t4i5/LedgerCore/issues/29) は「テストが薄い」ではなく、**壊して走らせた結果**を貼っている。

> `lib/screens/transaction_filter_sheet.dart` から `p.setSort(...)`（71 行目）と `resetFilters()`（83 行目）を両方削除して `flutter test` → 5 件すべて通る

これがあると「適用でソートが反映される、は壊しても誰も気付かない」が事実として確定し、再確認が要らなくなる。[#49](https://github.com/t1a2i3t4i5/LedgerCore/issues/49) の行数推移（`git log -- CLAUDE.md` の 8 コミット分）も同じ役割で、「肥大化している」という印象を「直近 8 コミットで +42%、減ったことは一度もない」に変えている。

## なぜ今これが問題になったか — 前提が壊れた瞬間を書く

省いてよい節。ただし **「前からそうだった」ものを今 issue にするなら必ず書く**。放置されてきたものを今日 issue にするからには、何かが変わっている。それが書かれていないと、読む側は「気になっただけ」と区別できない。

[#30](https://github.com/t1a2i3t4i5/LedgerCore/issues/30) は金額整形の 4 か所の重複を挙げているが、重複それ自体はずっと放置されていた。書いてあるのは変化のほうで、

> 単なる重複ではなくなった。PR #27 で DB の CHECK 制約がこの 4 か所を根拠にした

これで「4 か所のうち 1 か所だけ小数対応に変えるとスキーマ設計の前提が静かに崩れる」という実害に接続している。

## 提案 — どのファイルのどこに入るかまで書く

コード片を貼るなら diff 形式にして、入る位置を明示する。[#45](https://github.com/t1a2i3t4i5/LedgerCore/issues/45) は `summary_screen.dart` の `trailing` 差し替えを diff で示したうえで、**落とし穴も先に書いている**（`ListTile` は `trailing` を先に測るので、360px 幅で `title` の取り分が消えうる）。

実装しながら気付くはずのことを issue 側に書いておくと、着手した人が同じ壁で止まらない。

## 対象外 — やらない範囲を表で名指しする

**残すこと。** これを書かないと、レビューで毎回同じ拡張案が挙がり、そのたびに「今回はやらない」と口頭で答えることになる。書き手が意図的に外したのか、単に見落としたのかも区別できない。

[#45](https://github.com/t1a2i3t4i5/LedgerCore/issues/45) は変更する／しないを 4 行の表にしている。

| | 変更 | 理由 |
| --- | --- | --- |
| カテゴリ別リスト | **する** | 本題 |
| 円グラフの凡例 | しない | 扇形ラベルと % が二重になる |
| メンバー別リスト | しない | 今回の要望の対象外 |
| 合計カード | しない | 分母そのものなので常に 100% |

理由の欄が要点で、「しない」だけでは後から見て判断を再現できない。本題の行に「**する**」を 1 行入れておくと、表がそのまま差分の範囲になる。

この節は [`docs/git-workflow.md`](git-workflow.md) の `/review3` の運用と対になっている。差分の主題から外れる指摘を PR に押し込まず、かといって黙って捨てもせず、やらない範囲を名指しで残すためのもの。

## テスト — 壊し方まで書く

[CLAUDE.md](../CLAUDE.md) の「テストの書き方」に従う。不具合の issue なら、**実装のどこをどう壊せばそのテストが落ちるか**まで書く。落ちない書き方のテストを足しても、グリーンが増えるだけで何も守られない（`docs/testing.md` に並べた規約は、いずれも破っても静かにグリーンのまま通る類のもの）。

自動テストの対象外なら、その旨と手で確認する手順を書く。この issue 規約自体（[#55](https://github.com/t1a2i3t4i5/LedgerCore/issues/55)）がその例で、「Web UI の New issue に選択肢が出ること」「`gh issue create --template '課題・改善の記録'` で雛形付きのエディタが開くこと」を手順として置いている。

## 受け入れ条件 — 第三者が判定できる粒度で書く

**残すこと。** 無いと「どうなったら閉じてよいか」がどこにも書かれない issue になる。この規約を作った時点で、29 件中 19 件がそうだった。

粒度は、書いた本人以外が見て○×を付けられるところまで落とす。[#49](https://github.com/t1a2i3t4i5/LedgerCore/issues/49) の

> `CLAUDE.md` が 70 行以下 / 4,000 文字以下

は `wc` で判定できる。「読みやすくなっている」では判定できない。数値にできない場合でも「`docs/issue-writing.md` があり、各節について実例の issue 番号つきで理由が書かれている」のように、存在と形で判定できる形にする。

## 関連 — 切り出し元と、切り出した理由

関連 issue / PR を並べる。**ある PR から切り出したなら、なぜその PR で対応しなかったかも書く。**

[#29](https://github.com/t1a2i3t4i5/LedgerCore/issues/29) / [#30](https://github.com/t1a2i3t4i5/LedgerCore/issues/30) はどちらも PR #28 のレビューで挙がった指摘で、「金額欄とは独立した既存機能であり、PR #28 で新たに壊れたものではない」「差分の主題がぼやけ、レビュー範囲も広がる」と理由を残している。

これが無いと、後から見て「気付いていたのに、なぜ直さなかったのか」が失われる。指摘を issue に逃がす運用（`/review3`）を採っている以上、逃がした理由が記録の一部になる。

## CLI から使うとき

`--template` に渡すのは **front matter の `name`** であって、ファイル名ではない（`gh issue create --help` は `-T, --template name`、例も `--template "Bug Report"`）。`gh pr create` 側だけが `--template <file>` でパスを取るので混同しやすい。

```bash
gh issue create                              # テンプレートを選ばせる
gh issue create --template '課題・改善の記録'  # 雛形付きでエディタを開く
```

どちらも **対話（TTY）でのみ効く**。`--title` / `--body` を直接渡す非対話の呼び出し（Claude Code の Bash など）ではテンプレートは読まれず、渡した本文がそのまま issue になる。このリポジトリの issue はほぼこの経路で作られるので、**雛形が自動で入ることを当てにしない**。本文を自分で組み立てて `--body-file` で渡す。

```bash
# front matter を落として雛形だけ取り出す
sed '1,/^---$/d;1,/^---$/d' .github/ISSUE_TEMPLATE/issue.md > /tmp/issue-body.md
# /tmp/issue-body.md を埋めてから
gh issue create --title "..." --body-file /tmp/issue-body.md
```

`gh` も Web UI もテンプレートを**リモートのデフォルトブランチ**から取得する。テンプレートを変更した PR が main にマージされるまで、手元のブランチで `--template` を試しても反映されない。

## テンプレを `.github/` に置いている理由

「`CLAUDE.md` は索引、`docs/` が本文」という方針（#49）からすると `docs/ISSUE_TEMPLATE/` も候補になるが、採らなかった。

GitHub と `gh` が issue テンプレートを探すのは `.github/ISSUE_TEMPLATE/` / リポジトリ直下の `ISSUE_TEMPLATE/` / `docs/ISSUE_TEMPLATE/` の 3 か所だけで、ディレクトリ名も固定されている。`template/` のような任意ディレクトリは読まれない。PR テンプレート側は `gh pr create --template <file>` でパスを明示できるが、**issue 側にその逃げ道は無い** — `gh issue create` の `-T, --template` は規定ディレクトリ内のテンプレート *name* しか受け付けない。

残る `docs/ISSUE_TEMPLATE/` も正規のパスではあるが、`docs/` 配下だとディレクトリ名が GitHub 固定のため、人が読む解説文書（`db-schema.md` など）と機械が読む雛形が同じ階層に混ざる。`.github/` ならルート直下も増えず、将来 PR テンプレートを足すときに 1 か所へまとまる。

## テンプレートの種類は分けない

不具合・機能追加・docs で分けない。既存 issue は不具合寄り（#30）も機能追加（#45）も docs（#49）も骨格が同一で、分けても中身が同じものが増えるだけになる。増えた分だけ片方が陳腐化する。

Issue Forms（YAML 形式）も採らない。Web UI では入力欄を強制できる代わりに、**本文が Web のフォームでしか組み立てられない**。markdown の雛形なら、テンプレートが適用されない非対話の CLI からでも上記のように `--body-file` へ写せる（「CLI から使うとき」）。このリポジトリの issue はほぼ CLI 経由で、長い実装案やコードブロックを書く経路と噛み合わない。
