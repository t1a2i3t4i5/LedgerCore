# 設計上の約束と根拠

設計上の約束の本文（現在有効なもの）と、なぜそうしているか・破ると何が起きるかはこの文書を正本とする。[CLAUDE.md](../CLAUDE.md) は、コードを書く前に必要な結論だけを抜き出した索引。

## 集計ロジックは純関数に置く

`summary_calculator.dart` の `buildMonthlySummary` / `buildSplit` は DB に触らず、取引リストを受け取って結果を返す。DB アクセスと計算を混ぜないことでテストしやすさを保つ。

## Provider は `AppDatabase` を注入で受け取る

内部で生成しない。状態更新後は `notifyListeners()` を呼ぶ。

## 支払者は `Members`。表示層でも `memberId` / `memberName` と呼ぶ

`Transactions.memberId` が参照するのは `Members` テーブルで、**`Users` テーブルは存在しない**。このアプリにアカウントも認証もサーバもないので、`user` という語が指すものが実在しない。

表示層（`lib/models/` の `TransactionView` / `TransactionInput` / `MemberSummaryItem` / `MemberBalance`、集計、画面、Provider のフィルター）は長く `userId` / `userName` を使っていた。サーバ + REST API 構成から移植した名残で、名前が入れ替わる境目は `database.dart` の JOIN の詰め替え 1 か所だけだったので動作自体は正しかった。それでも「`userId` は認証済みユーザーの ID だ」と読める状態が残り、読む側が毎回「実際は members を指す」と読み替える必要があった。現在は `memberId` / `memberName` に揃えてある。

`User` 系の名前を戻さないこと。名前を真に受けた実装 — サーバとの通信を想定した構造、`userId` を認証済みユーザーの ID として扱うコード、レスポンスのパース処理 — が入っていないかを差分ごとに確かめる。テーブルと表示用モデルの対応表は [db-schema.md](db-schema.md) にある。

## 月の範囲指定は半開区間

`[月初, 翌月初)` で統一する（`getTransactionsByMonth` 参照）。

## 表示月の判断に画面から `DateTime.now()` を読まない

表示月の状態は `providers/month_scoped_provider.dart` の `MonthScopedProvider` に集約する。初期表示月・`isCurrentMonth`・`changeMonth`・`goToCurrentMonth` はすべて、Provider に注入された `clock`（既定 `DateTime.now`）1 つから導かれる。画面側で now を読み直すと判断材料が 2 層に分かれ、画面テストが実時刻に依存して月末に落ちる。

### 取引追加画面の既定日付はこの規則の対象外

`add_transaction_screen.dart` の `_spentAt` は意図的に実時刻を使う。表示中の月ではなく「今日」を既定にするのは、過去月を見返している最中に思い出した今日の出費を、徴候なく過去月へ沈めないため。表示月に寄せると「月しか選べない UI から日を捏造する」ことにもなる（`spentAt` の日は一覧のアバターとソートに効く）。**このずれは残す前提で、フィードバック側で誤認を潰す**（次項）。

### 保存先の月が表示月と違うことは、画面が言葉で知らせる

既定日付が表示月と独立している以上、両者がずれたまま保存する経路は残る。ずれたまま保存すると一覧にも合計にも何も現れず、成功したのに「保存に失敗した」ようにしか見えない。これを次の 2 段で潰す。

- 保存前: 日付欄の `helperText` に「表示中の 2026年7月 とは別の月です」を出す（事前に気づける）
- 保存後: 成功時は必ず SnackBar を出す。同じ月なら「保存しました」、別の月なら保存先を名指しした「2026年8月に保存しました」＋ `その月を表示` で移動できるようにする

**保存後に表示月を自動で切り替えない。** 結果は必ず見えるようになるが、ユーザーの閲覧文脈を無断で移すことになる。移るかどうかは `その月を表示` を押すかで本人が決める。

### アクション付きの SnackBar は `floating` にして FAB を避ける

SnackBar が出るのは `MainScreen` の Scaffold（ルートの `ScaffoldMessenger`）だが、FAB を持っているのは `TransactionsScreen` の入れ子の Scaffold なので、既定の `fixed` では FAB が押し上げられない。実測で `その月を表示` は FAB にぴたりと重なっており、続けてもう 1 件追加しようとしたタップがそのまま月移動になっていた。`behavior: SnackBarBehavior.floating` と下 88px の `margin` で FAB の上へ逃がす。

### タブを移ったら `hideCurrentSnackBar()` を呼ぶ

`main_screen.dart` の `onDestinationSelected` で呼ぶ。SnackBar はルートに出るのでタブを移っても残る。サマリータブで `その月を表示` を押せてしまうと、画面は何も変わらないまま取引一覧の表示月だけが裏で動く。

### 月をまたぐ操作は Provider 側で `fetch()` まで済ませる

`changeMonth` / `goToCurrentMonth` / `goToMonth` は表示月を変えたうえで再取得する。画面に `setYearMonth` と再取得を並べると、取引・サマリー・割り勘の 3 画面で同じ 2 行を書くことになり、片方だけ書き忘れると「月を送ったのに中身が前の月のまま」になる。`setYearMonth` は `@visibleForTesting` で閉じてあるので production からは使わない。

相対移動でない月ジャンプ（保存後の `その月を表示` など）は `goToMonth(year, month)` を使う。`changeMonth` に差分を計算して渡す書き方はしない — 呼ぶ側が年またぎの計算を持つことになる。

### 画面テストは `clock` を注入して固定年月で書く

詳細は [testing.md](testing.md) の「月を扱うテストは `clock` を注入して固定年月で書く」。

## 集計画面の期間モード（月／年／全期間）

### モードは画面の `State` ではなく Provider が持つ

`main_screen.dart` は `IndexedStack` を使わず `body: _screens[_currentIndex]` でタブを差し替える。**タブを離れると `SummaryScreen` の `State` は破棄される。** モードを画面に持たせると、取引タブを覗いて戻っただけで月モードに戻る。表示月が `SummaryProvider`（アプリ寿命）側にあるので、月だけ 2025 年 3 月のまま残りモードだけ初期化される、という半端な戻り方になる。

### 年の軸は表示月から独立させる（`_yearAxis`）

`SummaryProvider` は**集計タブと割り勘タブで 1 インスタンスを共有している**（`main.dart` の `MultiProvider` に 1 つだけ）。`MonthScopedProvider` の `year` / `month` は `fetch()` が月次サマリーと割り勘を取る対象そのものなので、**年送りでここを動かしてはいけない。**

最初の実装は `changeYear(delta) => goToMonth(year + delta, month)` で、「月の数値さえ保てば割り勘タブは無事」と考えていた。**これは誤りだった。** 月は保っても年が動くので対象期間は変わる。実測すると、割り勘タブは `2026年7月 / ¥700` から `2025年7月 / ¥250` に化けた。ユーザーは割り勘タブで何も操作していないので、金額が変わった理由が画面から分からない。

年モード・全期間モードが見る年は `SummaryProvider._yearAxis` という独立した軸に持たせる。年送りはこれだけを動かし、表示月には一切触らない。`isCurrentYear` / `goToCurrentYear` も年軸に対して定義する（`MonthScopedProvider` 側には置かない — あそこの `_year` は表示月の一部なので、同じ罠を次の人が踏む）。

**年モードへ入るときは年軸を表示月の年に合わせる。** 前に年モードで見ていた年を覚えていると、月モードで別の年へ移ったあとに年モードへ戻ったとき、今見ている月と無関係な年が出る。

この事故は「月が動かないこと」を見るテストでは捕まらない。`SplitResult.year` / `MonthlySummary.year` まで値で確かめる（`isNotNull` だけの確認では、前回 fetch の残骸が残る形の改変も素通りする）。

同じ理由で **`fetch()` は月次サマリーと割り勘をモードに関わらず常に取る。** issue #9 の「モード切り替えのたびに全部取り直さない」を素直に読むと年モードで `getSplit` を落としたくなるが、そうすると割り勘タブを開いた人に「データがありません」が出る。モードで出し分けるのは年次データ（`getYearlySummary` / `getYearlyTotals`）だけ。

使わないモードの年次データは捨てる。残すと「年を送る → 月モードへ戻す → また年モードへ」の途中で、前の年のグラフを一瞬描く経路ができる。

### 年モードにメンバー別を出さない

`YearlySummary` は `byMonth` と `byCategory` しか持たない。issue #9 は「年モードでも必要なら `buildYearlySummary` に追加する」と留保していたが、追加すると `models/summary.dart`・`summary_calculator.dart` と、既にテスト済みの `summary_calculator_test.dart` / `database_test.dart` まで波及する。カテゴリ別と違って「年間で誰がいくら払ったか」は割り勘タブの関心に近く、月単位の割り勘と二重に見える懸念もある。**足すなら別 issue で、割り勘を年単位にするかどうかと一緒に決める。**

### 全期間モードはグラフだけを出す

合計カードを出すには「年別合計の総和」を画面側で `fold` することになり、「集計ロジックは純関数に置く」約束に触れる。カテゴリ別も全期間ぶんを返す API が無い。issue #9 の表も全期間は「年別推移グラフ」だけ。

### 見出しか期間ナビを出したら、その下に必ず何かを描く

モードが 3 つに増えて空状態の分岐が増えたので、原則を 1 文に固定した。空表示は `_EmptySection` に寄せてあり、分岐ごとに書き写さない（片方だけ文言や余白がずれる）。

この整理で**既存の穴が 1 つ塞がった**。取引ゼロの月は `byCategory` も `byMember` も空になるが、ガードがあったのはカテゴリ別だけで、**メンバー別の見出しの下は無言の空白だった**。

## 金額は正の整数のみ

入力側（`add_transaction_screen.dart` の validator）と DB の CHECK 制約の二重で守る。上限は `models/transaction.dart` の `kMaxAmount` を両方が参照し、入力欄の桁数制限も同じ値から導出しているので、変えるときはそこだけを直す。片方にしか無い条件を足すと「画面では通るのに保存で落ちる」か、その逆になる。ただし割り勘の `fairShare` は `合計 ÷ 人数` の導出値なので小数のまま。

**`kMaxAmount` はスキーマ定義値でもある。** CHECK 制約にリテラルとして焼き込まれるため、値を変えるだけでは済まない。`schemaVersion` のインクリメントと移行、固定スキーマの再生成まで必要（[db-schema.md](db-schema.md) の「スキーマを変更するとき」）。

金額を描くウィジェットテストには `kMaxAmount` を使ったケースを置く（[testing.md](testing.md) 参照）。

## 金額の整形は `amount_format.dart` に集約する

### 入力欄は `AmountInputFormatter` を使う

`widgets/amount_format.dart` にあり、取引の追加・編集画面とフィルターシートが共有する。全角の正規化・記号の除去・桁数制限をここに閉じ込めてあるので、金額を入力する欄を新しく足すときも必ずこれを付ける。付け忘れると同じアプリ内で「追加画面では全角が通るのに、こちらでは理由の分からないエラーになる」という食い違いが出る。

### 表示側は `formatYen()` だけを通す

`NumberFormat('#,###', 'ja_JP')` は取引一覧・サマリー・割り勘・円グラフの凡例に個別に置かれていた。単なる重複ではない。`database.dart` の CHECK 制約が「全画面が小数部を出さない」ことを根拠に金額を整数に縛っているため、**4 か所のうち 1 か所を `#,##0.##` に変えるだけでスキーマ設計の前提が静かに崩れる**状態だった。変えた本人は画面の見た目を変えたつもりでいる。

`¥` まで含めて返すのは、記号を呼び出し側に残すと全角・半角やスペースの揺れが画面ごとに出るため。符号を前に出す割り勘の黒字表示だけは `'+${formatYen(x)}'` と外側で組み立てる。負値は `¥-1,200` の形になる。

割り勘の `fairShare` は「合計 ÷ 人数」なので小数を持つが、表示だけを丸める。計算は `double` のまま保つ。

書式を変えるときは `database.dart` の CHECK 制約と `AmountInputFormatter`（小数点を入力させない）を必ずセットで見直す。三者は互いの dartdoc / コメントから名指しで参照し合っている。

### 構成比は `formatRatio()` だけを通す

`formatYen()` と同じファイルに置いてある。金額の整形ではないが、**同じ行に並ぶ 2 つの数字の書式が対で決まる**ため隣に置く。`CategoryBreakdownRow` は金額と % を同じ上段へ置き、その下の `RatioBar` にも同じ `amount` / `total` を渡す。文字と帯で除算の入力を分けない。

導入当初（PR #65）は円グラフの扇形ラベルと集計画面のリストの 2 か所に同じ値が出ており、桁が食い違わないことが集約の主目的だった。**円グラフを外した今（PR #66 相当）、呼び出しは `category_breakdown_row.dart` の 1 か所だけ**だが、`toStringAsFixed` をウィジェットに書き戻さない。#9 の推移グラフのように、構成比を出す表示が再び増えたときに同じ食い違いが起きる。

**丸めて合計 100% にならないのは仕様。** 3 等分なら 33.3% × 3 = 99.9% になるが、補正する処理は入れない。

分母 0 のときは `-` を返す。金額は正の整数なので集計結果が空でなければ分母は正だが、取引ゼロの月を経由するので `NaN%` を描かせないために明示的に逃がしてある。

### 金額・構成比・カテゴリ名の幅を独立させる

以前のカテゴリ別リストは `ListTile.trailing` に金額と % を縦積みしていた。`ListTile` は `trailing` を先に測って残りを `title` に配分するので、`¥50,000 (14.3%)` のように 1 行へ連結すると 360px 幅で `title` の取り分が 43.5px しか残らず、**全角 4 文字のカテゴリ名が既に ellipsis で畳まれた**（実測値。縦積みなら 135.5px 残った）。

現在は `ListTile` を使わず、公開 `CategoryBreakdownRow` の上段 `Row` で「色ドット / `Expanded` の名前 / 金額 / 内容幅の構成比」を組む。**この罠は `ListTile` をやめた行にも形を変えて残る。** 固定側の金額と構成比が広がれば `Expanded` の名前は例外を出さず静かに畳まれる。`find.text()` も畳まれた `Text` にマッチするため、省略が起きたかは `RenderParagraph.didExceedMaxLines` で見る（`test/widgets/summary_screen_category_test.dart` の `_isEllipsized`）。

既定カテゴリは 2〜3 文字で幅不足の実装でも収まるため、**この回帰はユーザーが作る長さの名前でしか出ない**。テストのカテゴリ名を既定のものに戻さない。行は上段の数値と下段の帯を持つため、通常倍率では旧 `dense` の 48px ではなく `kCategoryBreakdownRowMinHeight` の 64px を基準にする。50 文字を ellipsis にしても通常倍率では伸ばさないが、端末の文字倍率を上げた場合は下端を切らないため必要量だけ伸ばす。

## カテゴリ別の構成比グラフは場所とエンコーディングで判定する

### 旧規則（2026-08 の #94 より前）

一度入れて外した。**「構成比が視覚的に分からないから円グラフを足そう」は差し戻しになる。**

PR #14 でドーナツグラフを入れた。当時のカテゴリ別リストは金額だけで、構成比はどこにも出ていなかったので、グラフが唯一の担当だった（issue #8 の動機がそれ）。ただし狭い扇形にラベルを載せると隣と重なるため、**構成比 5% 未満の扇形には % を出していなかった**（`_minLabelRatio = 0.05`）。細かいカテゴリほど割合が読めない、という裏返しの穴がここで生まれている。

PR #65 がその穴を埋めるためにリストへ構成比を併記した。この時点で情報の担当が逆転する。

| 情報 | ドーナツ | カテゴリ別リスト |
| --- | --- | --- |
| 構成比 | 5% 以上の扇形のみ | **全カテゴリ** |
| カテゴリ名 | 凡例 | `title` |
| 金額 | 凡例 | `trailing` |
| カテゴリの色 | 扇形 | `CircleAvatar`（`categoryColor()` で同色） |

ドーナツにしか無い情報が無くなり、しかも構成比に限ればリストのほうが多い。扇形ラベルとリストは同じ `formatRatio()` を通っていたので値も一致していた。縦 220px と凡例を占有して重複だけを出している状態だったため外した。

**空状態の「データがありません」は `CategoryPieChart` が出していた。** 取引ゼロの月でも `buildMonthlySummary()` は非 null の `MonthlySummary`（`byCategory` が空、`total` が 0）を返すので、`summary_screen.dart` の `summary == null` 分岐では受からない。グラフを消すときにこれを見落とすと、「カテゴリ別」見出しの下が無言で空白になる。受け皿は画面側の `byCategory.isEmpty` 分岐に移してある。

`fl_chart` と `chart_palette.dart` は残してあった。前者は #9（月別・年別の推移を棒グラフで表示）で使うため、後者はリストの `CircleAvatar` が現に使っているため。**その #9 で `widgets/period_bar_chart.dart` が入り、`fl_chart` の参照は復活している。** 当時ここで禁じていたのは「カテゴリ別の構成比をグラフにすること」であって、グラフ全般ではなかった。推移グラフはリストと情報が重複しない（時間軸はリストのどこにも出ていない）。

### 2026-08、#90 の一環として #94 で緩和した判定基準

旧規則を誤読の明確化として扱わず、カテゴリ別の構成比グラフを禁じる範囲そのものを次へ狭めた。

- **可:** 同じ値を**同じ行の中で**別のエンコーディング（長さ）に写すこと。`RatioBar` は 5% 未満も省略せず、正の比率には最小 2px を確保する。10 行の数値を一つずつ読まずに大小を走査できるという、数字だけでは担えない仕事があるため
- **不可:** 同じ値を**別の場所に第 2 の図として**置くこと。凡例を伴う図、カテゴリ別を独立した図として縦に積むこと、円 / ドーナツ / 扇形は、旧ドーナツと同じく表示領域と情報の担当を重複させる

空状態は引き続き画面側の `byCategory.isEmpty` 分岐が受け持つ。帯ウィジェットへ移すと、グラフを外した際に空表示まで失った旧事故を繰り返す。

## グラフウィジェットは `AppDatabase` も Provider も参照しない

表示データはすべて引数で受け取る。DB なしでウィジェットテストできる状態を保つ。`widgets/period_bar_chart.dart` は `List<PeriodTotal>` と高さ、`widgets/ratio_bar.dart` は `amount` / `total` / 色 / 高さだけを受け取る。

### グラフは自分で固定高さを持つ

集計画面はグラフを `ListView` の子として置く。`ListView` の子は高さ制約が非有界なので、高さを外から与えられる前提で書くと assert で落ちる。`PeriodBarChart` は `SizedBox(height:)` で自分を包む。

### 描画の崩れは `takeException()` では捕まらない

fl_chart は `Canvas` に直接描くので、**軸ラベルが隣と重なっても、はみ出しても、例外も overflow の縞模様も出さずに静かに切れる。** 削除した円グラフの `_chartHeight = 220` にも同じ注意書きがあった。検証手段の対応表は [testing.md](testing.md) にある。

とくに**棒グラフの X 軸には `SideTitles.interval` が効かない**（fl_chart が `barGroups` を全数走査して 1 群 1 ラベルを作るため）。間引きは `getTitlesWidget` の中で `SizedBox.shrink()` を返して自前でやる。知らずに `SideTitles(interval: 2)` と書くと、12 本のラベルが全部出て重なったまま無言で通る。

### 軸ラベルは幅だけでなく**高さ**も実測する

`SideTitles.reservedSize` は帯の太さで、fl_chart はその値で子の高さを tight に縛る（`SideTitlesFlex._computeSizes`）。`SideTitleWidget` が既定 8.0 を余白に使うので、`Text` に残るのは `reservedSize − 8`。

X 軸の帯を定数（22px）にしていたところ、**端末の文字サイズを 1 段階上げただけでラベルの下端が切れた**。実測では scale 1.0 で 13.0px、1.15 以降は 14.0px で頭打ちになり、理想の行高（17.3px / 26.6px）に届かない。`overflow: TextOverflow.ellipsis` を指定した `Text` は縦にはみ出した分を `_needsClipping` で黙って切るので、例外も縞模様も出ず、`didExceedMaxLines`（行数の超過）にも引っかからない。

幅だけを `TextScaler` 込みで実測して高さを定数にすると、**重なりの検査もすり抜ける**（幅は足りているため）。`TextPainter` の `size` を使い、幅と高さを一緒に採る。

間引きは**末尾を起点にする**。先頭起点だと、間引きが効いた瞬間に右端（いちばん新しい期間）のラベルが落ちることがある。読み手が最初に見るのは直近なので、そこは必ず残す。

## グラフの色は `chart_palette.dart` に集約する

`categoryColor(categoryId)` はカテゴリ ID から決定的に色を選ぶので、同じカテゴリはどの画面でも常に同じ色になる。現在の利用箇所は集計画面の `CategoryBreakdownRow` の色ドットと `RatioBar`。画面側で解決してウィジェットへ渡し、ウィジェット内に色を直書きしない。

`memberColor(memberId)` はカテゴリ用と交わらない別パレットから同じ性質を提供する。#93 で追加したが、メンバー別行を `ListTile` のまま維持する #94 時点では production の利用箇所はまだ無い。割り勘画面などでメンバーの識別色を使うときはこの関数を入口にする。

### 推移グラフの棒は `trendColor(colorScheme)` を使う

`categoryColor()` を流用しないこと。あれはカテゴリ ID から色を選ぶ関数なので、カテゴリと対応しない棒に使うと「食費と同じ色」という無意味な結び付きが画面上に生まれ、意味のある対応に見えてしまう。

固定色を直書きせず `ColorScheme.primary` に委ねているのは、推移グラフの棒が「その画面の主役の 1 色」でしかなく、カテゴリのように**互いを区別する**必要が無いため。テーマから採ればダークテーマでも自動でコントラストが保たれる。ツールチップは背景にこの色を敷いて文字を載せるので、文字色は `labelColorOn()` で輝度から選ぶ（棒の色を変えたときに文字が背景へ溶ける経路がここで塞がる）。

## Y 軸のラベルだけは `formatYen()` を通さない

`widgets/amount_format.dart` の `formatYenAxis()`（`¥1兆` `¥12.5万` の形）が唯一の例外。`formatYen()` をそのまま軸に使うと `kMaxAmount` が `¥999,999,999,999` の 15 文字になり、360px 幅の 3 分の 1 以上を Y 軸が占めてグラフ本体が潰れる。この値は DB の CHECK 制約が現に許すので「そんな金額は入らない」では逃げられない。

**この例外をウィジェット内に隠さないこと。** 金額の書式を各所で組み立て直さないのが規約の実質であり、`formatYen()` が小数部を出さないことは DB の整数 CHECK 制約の根拠そのものなので、**丸めて小数を出す関数は `formatYen()` の隣に、なぜ例外なのかを書いて置く**必要がある。グラフの中に隠すと、CHECK 制約の根拠を読みに来た人がこの例外を見つけられない。

丸めた概数には必ず単位（万・億・兆）を付ける。実額と見分けが付かない形で丸めると、金額が静かに嘘になる。小数第 1 位までで足りるのは、呼び出し側が目盛りを 1/2/5 × 10^n の倍数に丸めてから渡すため（目盛り幅は最大値の 4 分の 1 以上、つまり単位の 0.2 以上になる）。

### 目盛りは 1 円を下限にする

金額は正の整数しか入らないので、目盛りが 1 円未満になると**存在しない額が軸に並ぶ**。1 円の取引 1 件だけを登録した状態が実際にその条件で、`1 ÷ 4 = 0.25` から 0.5 円刻みが選ばれ、`formatYen()` が 0.5 を四捨五入して `¥0 / ¥1 / ¥1` と**同じラベルが 2 つ**出ていた（実測。合計 2 円なら `¥1` と `¥2` が 2 つずつ）。

「金額は正の整数のみ」という約束は入力と保存だけの話に見えるが、**軸の刻みもその約束の内側にある**。`_niceInterval` の戻り値を 1 で下限クランプして揃えてある。

## 年月の整形は `period_format.dart` に集約する

`'$year年$month月'` を画面ごとに書くと、月選択のヘッダと推移グラフのツールチップで書式が食い違う。金額に対する `amount_format.dart` と同じ発想で 1 か所に閉じる。

現在ここを通るのは 4 経路。**新しく関数を作るときは、既存の組み立て箇所を移すところまでが 1 セット。** 移さずに「これからはここに集約する」とだけ書くと、唯一の置き場を自称するファイルが 2 つある状態になる（実際 1 度そうなった）。

- 月選択のヘッダ（`month_selector.dart`）
- 推移グラフのツールチップ（`period_bar_chart.dart`）
- 取引追加画面の案内 2 か所（`add_transaction_screen.dart` の日付欄 `helperText` と保存後の SnackBar）
- 集計画面の合計カード（`summary_screen.dart` の月 / 年ラベル）

3 つ目は見落としやすいが、**月選択のヘッダと並べて読ませる文言**なので外せない。「表示中の 2026年7月 とは別の月です」の年月だけ形が違うと、同じ画面に 2 通りの書式が同時に出る。

長い形（`formatPeriod`）と短い形（`formatPeriodShort`）を対で持つのは、**軸の幅に応じてどこまで書くかが変わる**ため。12 本並ぶ月別グラフの軸に `2026年7月` を出すと、360px 幅では 1 本あたり約 22px しかないので必ず重なる。一方でツールチップは長い形を使う — 軸ラベルは間引かれることがあり、間引かれた棒をタップしたときに何月か分からなくなるため。

`models/summary.dart` の `PeriodTotal` が表示用の文字列を持たないのはこの判断が画面側の責務だから。モデルにラベルを持たせると、軸とツールチップで別の形が要るたびにモデルが増える。

## 操作ログは端末内のファイルへ JSON Lines で追記する

出力先は `lib/logging/` が持つログファイル 1 本だけ。**drift のテーブルには入れない。**
このアプリに通信は無いので、ログの用途は「端末の持ち主が後から自分の操作を追う」に閉じている。
DB に持たせると `schemaVersion` の引き上げ・固定スキーマの再生成・移行ヘルパまで一式が必要になるが、
得られるのは画面表示のしやすさだけで、その画面を作らない以上は払い損になる。

形式は 1 行 1 JSON（JSON Lines）。行ごとに独立しているので、途中の行が壊れてもその行だけ捨てて読み進められる。
キーの順は `ts` → `lv` → `op` → `detail` → `error` に固定してある（`toJsonLine` が組み立て順で決める）。
目で追う前提の形式なので、行ごとに列が動かないことに意味がある。**`jsonDecode` して Map で比較するテストを書くと
この順序が守られなくなる**ので、`log_entry_test.dart` は出来上がった文字列そのものを期待値に置いている。

`lv` は `info` と `error` の 2 値だけにする。`debug` / `warn` を足すと「どちらで出すか」の判断が
呼び出し側 20 箇所以上に散り、実際には全部 `info` になる。

### ログの書き出しは呼び出し側に await させない

`OperationLogger.info()` / `.error()` は `void` で、行の組み立て（時刻の確定を含む）まで同期で済ませてから
内部のキューへ積んで即座に戻る。`create()` の中で `await logger.info(...)` を書くと、取引の保存が
ファイル I/O を待つぶんだけ遅くなる。ログのために操作の応答を落とすのは順序が逆。

キューは**単一の `Future` チェーン**にする。各呼び出しが独立に `write` を始める形にすると、
行の順序が I/O の完了順に化けて「削除のあとに追加」が記録される。
書き込みの完了を待ちたいテストは `flush()` を使う。production からは呼ばない。

**チェーンの起点を `Future.value()` にしない**（`_pending` は `null` から始める）。コンストラクタが
走った時点のゾーンに属する `Future` を起点にすると、そこへ繋いだコールバックもそのゾーンで動く。
`setUp` でロガーを作って `testWidgets` の中で `info()` を呼ぶ形だと、書き出しが擬似時間のゾーンから
流れなくなり、`pump` しても行が 1 つも書かれない（実際にこれで画面テストが 4 本とも空振りした）。

時刻は**キューを消化する時点ではなく呼び出し時点で確定する**。消化時に読むと、書き込みが詰まったぶんだけ
実際の操作時刻から後ろへずれる。

書き込み中の例外は握りつぶす（`debugPrint` にだけ落とす）。ここで例外を通すと、書き込み先が埋まった端末で
家計簿そのものが操作不能になる。ログが欠けるほうが軽い。同じ理由で、ロガーの初期化に失敗した端末は
`NoopLogSink` に倒して**必ず起動する**（`main.dart` の `_createLogger`）。

### 書き込み系に足した `try` は必ず `rethrow` する

`create` / `update` / `delete` は元々 catch していなかった。例外は Provider を素通りして画面側
（`add_transaction_screen.dart` / `categories_screen.dart` / `members_screen.dart`）の catch に届き、
SnackBar になる。**失敗をログに残すために足した `try` は、この経路を壊してはいけない。**
`rethrow` を落とすと、保存に失敗しても画面には何も出ず、ユーザーには成功したように見える。

`provider_logging_test.dart` の「保存に失敗すると error が残り、例外は呼び出し元まで届く」がこの回帰を見ている。
金額 0 は DB の CHECK 制約に弾かれるので、例外を起こす手段として使える
（閉じた DB への削除は例外にならないので使えない）。

### 取引のメモ本文はログに書かない

家計簿のメモは「◯◯病院」「◯◯さんへの祝儀」のように機微になりうる一方、ログファイルは端末外へ持ち出されうる。
`memoLength`（文字数）だけを残す。同じ理由で**フィルターのメモ検索語も残さない**（`hasMemoQuery` の真偽だけ）。
「◯◯病院」で検索した事実が残るのは、本文が残るのとほとんど変わらない。

カテゴリ名とメンバー名は載せる。ユーザー自身が付けた短いラベルで、画面に常時出ている情報のため。

**`detail` から外すだけでは漏れる。** 同じ行の `error` に載る例外文字列にメモ本文が入っていた。
`sqlite3` の `SqliteException.toString()` は失敗した文に続けて `, parameters: 1, 1, 0.0, ..., ひみつの通院, ...`
とバインド値を全部並べるため、保存や更新が DB 側で失敗したときだけ `detail` に `memoLength:6` と
本文が並ぶ 1 行が書かれていた。到達経路は金額の CHECK 制約違反・FK 違反・空き容量不足（`SQLITE_FULL`）で、
どれも普通に起きる。`kMaxErrorLength`（1000 文字）の切り詰めも、値が 470 文字付近に出るので効かない。

対策として `log_entry.dart` の `sanitizeError()`（純関数）を通してから `LogEntry.error` に載せる。
**落とすのは `, parameters:` からその行の終わりまでだけ。** `Causing statement:` の文そのものは
プレースホルダ（`VALUES (?, ?, ...)`）しか含まないので残す — どの文で落ちたかは失敗の追跡に要る。
行末で止めるのは、`main.dart` の `app.uncaught` が例外の後ろにスタックトレースを繋げて渡してくるため。
例外以降を丸ごと捨てるとスタックまで消える。例外の型ではなく文字列で判定するのは、`sqlite3` が
推移的依存で `test/matchers.dart` も文言で判定しているのと同じ理由。

`sqlite3` が書式を変えれば黙って漏れが戻るので、回帰テストは**実 DB を失敗させて**書く
（手で組んだ例外文字列だけでは書式の変化を捕まえられない）。

### 未捕捉の非同期例外はコンソールへも出し直す

`runZonedGuarded` を挟むと、それまで未捕捉の非同期例外を stderr へ出していた Dart 既定のハンドラが
第 2 引数のハンドラに置き換わる。ログに書くだけだと `flutter run` 中のコンソールから例外が消え、
ロガーが `NoopLogSink` に倒れた端末ではどこにも残らない。ハンドラの中で `debugPrint` も呼ぶ。
同期側の `FlutterError.onError` が `presentError()` を呼び直しているのと揃える。

### 上限はバイトで測り、退避は 1 世代だけ

`shouldRotate` は「現在サイズ + 追記ぶん」で判定する。書いた後に判定すると上限を必ず 1 行ぶん超えてから交代する。
上限は**文字数ではなくバイト**で測る。日本語のカテゴリ名が入るので、文字数で数えると実ファイルは 3 倍近くまで膨らむ。

**現在サイズが 0 のときは交代しない。** 1 行だけで上限を超える場合に効く。交代しても移した先が空になるだけで、
その行は結局どこかに書かれる。判定を通すと「毎回 rename して毎回空ファイルに書く」形になり、
行が 1 本ずつ別ファイルへ散ってすべて失われる。

`detail` を JSON へ均す `_normalize` には深さの上限がある。循環参照で自分自身を呼び続けると
`StackOverflowError` になり、`OperationLogger` がその行を丸ごと捨てるため。畳んだ文字列でも
「何が入っていたか」は残るので、行ごと消えるよりましになる。

### `testWidgets` の中では `flush()` を待たず `pump()` で流す

素の `await logger.flush()` を `testWidgets` の中に書くと**返ってこない**。キューは `info()` を呼んだ
擬似時間のゾーンに積まれ、そのマイクロタスクはフレームを進めないと流れないため。`pumpAndSettle` の既定
タイムアウトが 10 分あるので、失敗ではなく長いハングに見える。

`tester.runAsync()` で包むのは**誤り**。擬似時間を止めて実時間で走らせるので、キューを流す側と待つ側が
互いを待ってデッドロックする。`await tester.pump()` を 1 つ挟むのが正解
（`main_screen_logging_test.dart` の `flushLog`）。

### 時刻とタブ名の書式はログ専用に持つ

ログの年月は `2026-08`（`month_scoped_provider.dart` の `_logMonth`）、時刻はミリ秒 3 桁固定
（`formatLogTimestamp`）。画面用の `formatPeriod()`（`2026年8月`）を使い回さないのは、ログが機械可読を
優先して桁を固定するため。`DateTime.toIso8601String()` を使わないのも同じ理由で、あちらはマイクロ秒の有無で
小数部が 3 桁と 6 桁を行き来する。

タブ名も画面の文言（`_titles`）とは別に英字の `_logNames` を持つ。`op` が英字なので detail も英字で揃い、
画面の文言を変えてもログの集計が壊れない。**この書式を画面に出さないこと** — 年月の表示は今までどおり
`period_format.dart` に寄せる。

`op` は `<対象>.<動作>`、`lv` は `info` / `error` の 2 値だけ。レベルを増やさない。

## 配色・書体・形状はテーマ層に集約する

画面と共通ウィジェットは、Material の意味を持つ色を `Theme.of(context).colorScheme` から、
アプリ固有の補助色・角丸・影・金額書体を `lib/theme/ledger_tokens.dart` の
`LedgerTokens` から採る。画面側に `Colors.*` や `Color(...)` を直書きしない。

以前は `main.dart` の `ThemeData(colorSchemeSeed: Colors.teal)` だけがテーマ定義で、
`Theme.of(context)` 経由の色参照は 1 か所しかなく、残る 22 か所は画面へ直書きされていた。
そのため seed を変更しても大半の画面へ届かず、アプリ全体の配色を一貫して変更できなかった。
現在は `ledger_theme.dart` が `ColorScheme.fromSeed` をブランド色から作り、必要なロールを
`copyWith` で確定する。未指定の Material ロールも同じ暖色系の seed から導かれる。

`surfaceTint` は透明に固定する。Material 3 は既定で elevation のある面へ `primary` を
重ねるため、指定しないと白い `Card` や BottomSheet が濃茶を帯びる。
`test/widgets/ledger_theme_test.dart` は `Card` が最終的に白で描かれることを、テーマ定義の
値ではなく解決後の `Material.color` で守る。

アプリはライトテーマだけを持ち、`LedgerTokens` は `ThemeExtension` にしない。差し替える
テーマ実体と補間が無い現状では、`ThemeExtension` は null 許容のルックアップを増やすだけに
なるため。ダークテーマを導入する場合は、その時点で `ThemeExtension` への移行を検討する。

`LedgerTokens.subtext`（`#A39288`）は白いカード上で約 2.4:1 と WCAG AA を満たさない。
デザイン案の値を優先する一方、日付・補足ラベルなどの補助情報にだけ使い、本文サイズ以上の
主要情報には使わない。`chart_palette.dart` の文字色は塗りの上で AA 4.5:1 を守る別用途で、
この例外を適用しない。

### 期間を選ぶ部品は共通の形を使う

取引一覧・集計・割り勘の年月見出しは `MonthSelector` に集約し、月を 38px、年を
Outfit 16px の二段で描く。前後移動と「今月／今年」は右側の 38px 角丸ボタンにまとめる。
画面ごとに `style` を渡すと同じ期間の見た目が割れるため、呼び出し側では上書きしない。
二段見出しの文字列は `formatPeriodHeader()` から受け取り、画面側で年月を組み立てない。
可視の `Text.rich` 自体が従来の長い年月を読み上げとテストへ公開するので、検査専用の
不可視 `Text` は置かない。

「今月／今年」は 38px の中でラベルが欠けないよう、文字倍率を最大 1.5 倍に制限する。
固定サイズのまま端末倍率 2.0 を通すと全角 2 文字が折り返され、後半が無言で切れるため。

`SegmentedButton` は Material 3 既定の外側のピル形状を使い、選択色と枠線は
`ledgerTheme.segmentedButtonTheme` が共通で持つ。Flutter は各セグメントの shape を
角丸 0 で上書きするため、テーマの shape で「選択面もピルになる」とは扱わない。
集計画面と取引フィルターで個別に `style` を組み立てない。選択面は白、文字は
`ColorScheme.onSurface` とし、通常サイズ文字のコントラスト比 4.5:1 以上を保つ。
白い BottomSheet 上でも外形と境界が消えないよう、`outlineVariant` の枠線を残す。

## コード整形は language version で決まる

`dart format` のスタイルは、実行中の Dart SDK ではなく **language version** で決まる。現在は Dart 3.7 の tall style。

**`dart format` が読むのは `.dart_tool/package_config.json` の `languageVersion` であって `pubspec.yaml` ではない。** `pubspec.yaml` の `environment.sdk` の下限（現在 `>=3.7.0`）はその元になる値で、`flutter pub get` を通して初めて `package_config.json` に反映される。

- **下限を動かしたら必ず `flutter pub get` を走らせる。** 飛ばすと `dart format` は古い `languageVersion` のまま整形する。`dart format` は `dart run` や `flutter test` と違って暗黙の pub get をしないので自己修復しない
  - しばらく触っていないクローンでは `package_config.json` が古いことがある。`.dart` を編集する前に `flutter pub get` を通す。古いまま編集すると、`3.0` の頃の値で 63 ファイル中 30 ファイルが旧スタイルへ書き戻る
- **下限を動かすと全 `.dart` ファイルが再整形の対象になる**。依存更新のついでに触らない。変えるなら整形だけを独立した PR にする
- 下限を下げると旧スタイルに戻る。スタイルが混ざっている箇所を見つけても、そのファイルだけ手で直さない（`dart format` を通す）
- 生成物（`lib/db/database.g.dart` / `test/generated_migrations/*.dart`）も同じ language version で整形されて出る。`build_runner build` と `drift_dev schema generate` のどちらを回しても差分は揺れない
- Claude Code で作業する場合、`.claude/settings.json` の `PostToolUse` フックが `.dart` の編集直後に `dart format` を自動実行する。`jq` に依存している
