issue を 1 本の PR にします。**実装 → テスト → コミット → PR 作成までで終わります** — レビューもマージもしません。作成した PR は `/independent-review <番号>` へ渡します。

issue: `$issue`

## 処理の流れ

| #   | 手順                                                                                          | 中断条件                                                             |
| --- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 0   | **作業ツリーを確かめる** — `flutter pub get` より前に見る                                     | 作業ツリーが汚れている・現在のブランチに未 push のコミットがある     |
| 1   | **issue と規約を読む** — 全文とコメント、`CLAUDE.md`、領域に応じた `docs/*.md`。最後に `flutter pub get` を 1 回通す | issue が存在しない・closed・同じ issue の PR が既に open              |
| 2   | **着手可否を判定する** — 「対象外」と「受け入れ条件」を作業リストに写し、仕様の穴だけを聞く   | （なし。穴は質問で埋める）                                            |
| 3   | **ブランチを切る** — `origin/main` 起点                                                        | `git fetch` が失敗                                                    |
| 4   | **実装する** — 既存の口を再利用する                                                            | 仕様の穴が新たに出た（追加の質問バッチを 1 回だけ許す）              |
| 5   | **生成物を再生成する** — DB 定義を触った場合のみ                                               | 定義を変えたのに生成物に差分が出ない                                  |
| 6   | **テストする** — 壊し方があれば実際に落ちることを確かめる                                      | 落ちるテスト・`error` を直せなかった                                  |
| 7   | **docs を追従させる**                                                                          | （なし）                                                              |
| 8   | **コミット → push → PR 作成 → 報告**                                                        | rebase が conflict した                                               |

**承認ゲートは置きません**（既定値。変更する場合はコメントで指示）。止まるのは中断条件と、仕様の穴を聞くときだけです。

## 現在の状況

- ブランチ: !`git branch --show-current`
- 作業ツリー: !`git status --porcelain || echo "（クリーン）"`
- 未 push のコミット: !`git log --oneline origin/main..HEAD || echo "（なし）"`
- open な issue: !`gh issue list --state open --limit 20 --json number,title -q '.[] | "#\(.number) \(.title)"' || echo "（取得できず）"`

## 0. 作業ツリーを確かめる

**`flutter pub get` より前に、いちばん最初に判定します。** `pub get` は `pubspec.lock` を書き換えることがあり、後から見るとこのスキル自身が作った差分で「汚れている」と中断します。原因が自分だと分からない報告になるので、順序で防ぎます。

```bash
git status --porcelain
git log --oneline origin/main..HEAD
```

- **`git status --porcelain` の先頭が `??` でない行が 1 行以上** → 中断して報告します。**`git stash` も `git commit` も勝手にしません**（ユーザーが作業中の変更を勝手に動かさない）
- **`git log --oneline origin/main..HEAD` が 1 行以上** → 中断して報告します。手順 3 でブランチを切ると、そのコミットが置き去りになります。`origin/main` との差分で見るので、upstream の設定に依存しません

未追跡ファイル（`??`）だけがある状態は「汚れている」に**含めません**。一時ファイルが 1 つ残っているだけで着手できなくなるためです。ただし**報告にはパスを列挙します**。

worktree の中で動いている場合は、そのまま使います。新しい worktree を作りません（手順 3 が `origin/main` 起点なので、追加の分岐が要りません）。

## 1. issue と規約を読む

### 引数を解決する

先頭の `#` と全角 `＃` を落とします（`＃7着手してください` の形で来ます）。

**引数が無いとき**は open な issue を**番号の昇順**で出し、次のとおり分岐します。**勝手に選びません。**

| open の件数 | 挙動                                                    |
| ----------- | ------------------------------------------------------- |
| 0 件        | 「着手できる issue が無い」と報告して終わる             |
| 1〜4 件     | `AskUserQuestion` の選択肢にして選ばせる                |
| 5 件以上    | テキストで一覧を出し、番号の指定を求めて終わる          |

### issue を読む

```bash
gh issue view <番号> --comments
gh issue view <番号> --json state
gh pr list --state open --search "<番号>"
```

- **`gh issue view` が失敗する**（番号が存在しない） → 中断して報告し、**open issue の一覧を添えます**
- **`state` が `CLOSED`** → 中断して報告し、**クローズコメントを添えます**。勝手に着手しません（見送りの判断が済んでいることがあります）
- **同じ issue の PR が既に open** → 中断して報告し、**PR 番号を添えます**

コメントまで読みます。仕様の変更や追加の判断が、コメント側にだけ書かれていることがあります。

### 規約を読む

`CLAUDE.md` は常に読みます。加えて、触る領域に応じて次を読みます。

| 触る領域                        | 追加で読む                                                     |
| ------------------------------- | -------------------------------------------------------------- |
| 常に                            | `CLAUDE.md`、`docs/issue-writing.md` の別名表（14-20 行）      |
| `lib/db/`                       | `docs/db-schema.md`                                             |
| `test/`                         | `docs/testing.md`                                               |
| `lib/` の `db/` 以外            | `docs/design-notes.md`                                          |
| `docs/` / `.github/` の issue 関連 | `docs/issue-writing.md`                                      |

「触る領域」は issue の「追加・変更するファイル」（ツリー図）を根拠に決めます。**それが無い issue では 4 つとも読みます。** この時点では領域が確定していないので、狭く見積もると `test/` を書くのに `docs/testing.md` を読まない経路ができます。

### `flutter pub get` を通す

**領域に関わらず、手順 1 の末尾で必ず 1 回走らせます。**

```bash
flutter pub get
```

`dart format` が読むのは `.dart_tool/package_config.json` の `languageVersion` で、しばらく触っていないクローンでは古いままです。編集より前に通しておかないと、`.dart` の編集直後に走る `PostToolUse` フックの `dart format` が旧スタイルで整形します（`CLAUDE.md` の「コード整形」）。DB を触るかどうかとは無関係なので、手順 5 の条件付き実行に混ぜません。

## 2. 着手可否を判定する

「対象外」表と「受け入れ条件」を、そのまま作業リストに写します。**この 2 つが実装範囲と完了判定です。**

### 節名は揃っていない — 別名を吸収する

節の骨格を定めた `docs/issue-writing.md` より前に書かれた issue が大半です。**節名のリテラル一致で分岐すると、issue が既に答えていることを聞き直したうえで、範囲指定を捨てることになります。**

別名の唯一の情報源は `docs/issue-writing.md:14-20` の表です。そこに載っていないものだけをここに足します。

| 役割       | 正式名     | 表に無い別名        |
| ---------- | ---------- | ------------------- |
| 完了の判定 | 受け入れ条件 | `合格条件`（#54） |

**該当する節がどうしても無いときだけ**、次のように補います。中断はしません。

| 欠けている節 | 補い方                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------- |
| 完了の判定   | issue 本文から**こちらで起草し、質問バッチの 1 問目で確認する**。判定できないまま実装しない  |
| やらないこと | issue 本文が名指ししたファイルだけを変更範囲とする。そこに無いファイルを触る必要が出たら、下の穴 2 に当たる |

**「節が無い＝穴ゼロ」と評価して、黙って実装を始めないこと。**

### 「仕様の穴」の判定

**`## 判断が要る点` があれば、そこが未決事項の一覧です。** 穴を探す前に、まずこの節を見ます。

そのうえで、次のいずれかに当たるものだけを穴とします。**それ以外は既定値で決めて進みます。**

1. 「受け入れ条件」のどれかが、実装しても ○× を判定できない
2. 「対象外」表に無い変更が必要になった（範囲が変わる）
3. `## 提案` 配下の `###` に無い値を決める必要があり、既存コードと `docs/design-notes.md` からも一意に決まらない

穴が見つかったら `AskUserQuestion` で **1 バッチ（最大 4 問）**聞きます。推奨案を先頭に置き、ラベル末尾に `（推奨）` を付けます。**回答を待つあいだ、コードを書きません。**

**5 個以上出たら、影響の大きい順に 4 問だけ聞きます。** 1 バッチ 4 問までなので、2 バッチ目は出しません。残りは既定値で決めて、**PR 本文に「判断したこと」として列挙します**。手順 4 で新たに出た場合のみ、追加のバッチを 1 回だけ許します（実装を始めて初めて見える穴があるため）。

## 3. ブランチを切る

```bash
git fetch origin && git switch -c <prefix>/<kebab-case> origin/main
```

`git fetch` が失敗したら中断して報告します。

**`main` に切り替えず、`origin/main` から直接切ります。** worktree の中では `main` が親 worktree に占有されていて `git switch main` が落ちるためです（`docs/git-workflow.md` の「worktree から `gh pr merge` すると…」と同じ制約）。`origin/main` 起点なら worktree でも通常の作業ツリーでも同じ 1 行で済み、分岐が要りません。

- **接頭辞** — `docs/git-workflow.md:67-74` のブランチ命名規則の表から、issue の内容で選びます
- **ブランチ名** — `kebab-case`。**issue 番号は付けません**（既定値）。例外は 1 つの issue を複数 PR に分けるときだけです（`feat/9-period-bar-chart` / `feat/9-summary-period-ui`）

## 4. 実装する

データの流れは `screens → providers → AppDatabase` の一方向です。詳細は `CLAUDE.md` と `docs/design-notes.md` を読んでください（ここには写しません）。

**既存の口を再利用し、新規に作り直しません。** issue が「この既存メソッドを使う」と名指ししているなら、そのとおりにします。名指しが無くても、同じことをする関数が既にないかを `grep` で先に確かめます。

実装中に**新たな仕様の穴**（手順 2 の 3 条件）が出たら、そこで止めて `AskUserQuestion` を **1 回だけ**追加で出します。それ以外は既定値で決めて進み、決めたことは PR 本文に残します。

## 5. 生成物を再生成する

**`lib/db/database.dart` のテーブル定義か `@DriftDatabase` を触った場合だけ**走らせます。触っていないなら飛ばします。

| 触ったもの                      | 走らせるもの                                                    |
| ------------------------------- | ---------------------------------------------------------------- |
| テーブル定義 / `@DriftDatabase` | `dart run build_runner build`                                     |
| `schemaVersion` を上げた        | 上に加えて `drift_dev schema dump` / `drift_dev schema generate` |
| `pubspec.yaml`                  | `flutter pub get`（手順 1 とは別にもう一度）                     |

コマンドの正確な形は `README.md` の「開発コマンド」、生成物を git に含める条件は `CLAUDE.md` の「drift のコード生成」にあります。

**定義を変えたのに `git status` に `lib/db/database.g.dart` が出てこないときは中断して報告します。** `build_runner` のキャッシュが古い成功表示を返している可能性があります（成功と出ても `.g.dart` が古いままになる）。

## 6. テストする

```bash
flutter test
flutter analyze
```

- **`flutter test` が全件通ること**
- **`flutter analyze` に `error` が 0 件であること。** `info` / `warning` は許容し、**件数を PR 本文に書きます**

直せなかったとき（落ちるテスト・残った `error`）に中断して報告します。**落ちたまま PR を作りません。**

### 壊して確かめる

issue の「テスト」節に壊し方が書かれていたら、**実際にそのとおり壊して、テストが落ちることを確かめてから元に戻します。**

- **落ちた** → そのまま進みます
- **壊しても落ちない** → そのテストは何も守っていません。**テストを書き直してから進みます**（中断しません）

**壊し方が書かれていない issue では、質問に回しません。** `flutter test` と `flutter analyze` の全件通過で進み、**PR 本文に「issue に壊し方の記載が無かった」と書きます**。

壊したら必ず元に戻します。戻し方は「壊す前の内容を控えておき、`Edit` で書き戻す」です。**`git checkout -- <file>` を使わないこと** — 同じファイルにある実装中の変更ごと消え、復元できません。

## 7. docs を追従させる

| 変えたもの             | 追従先                                  |
| ---------------------- | ---------------------------------------- |
| スキーマ               | `docs/db-schema.md`                      |
| 新しい設計上の約束     | `docs/design-notes.md` と `CLAUDE.md`   |
| git / issue の運用     | `docs/git-workflow.md` / `docs/issue-writing.md` |

条件は `CLAUDE.md` の各節にあります。**同じコミットに含めます。**

## 8. コミット → push → PR 作成 → 報告

### コミット

論理単位で小さく分けます。メッセージは日本語で、末尾に次を付けます。

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

### push

```bash
git push -u origin <branch>
```

**rejected されたら `git pull --rebase origin main` して再 push します。** **conflict したら `git rebase --abort` して中断・報告します。自動で解決しません。**

### PR を作成する

```bash
gh pr create --title "<タイトル>" --body-file <本文のパス> --base main
```

`--body-file` で組み立てます。`.github/` に PR テンプレートは無く、非対話ではテンプレートが発火しないためです。**`--draft` を付けません** — 作成直後に `/independent-review` へ渡せる状態にします。

|              |                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------- |
| タイトル     | issue のタイトルをそのまま使わず、**実際にやったことを動詞で終える**                        |
| 本文 1 行目  | `Closes #<番号>`                                                                             |
| 以降         | 「やったこと（判断の理由を厚く）」→「テスト（件数と観点、壊して赤くなることの実測）」の順 |
| 見出し       | **固定しません。** 内容に合うものを選びます。ただし `## 変更点` は使いません（このリポジトリの全 PR で 0 件） |

**`Closes` を書かない例外**: issue に「マージ後に判定する」受け入れ条件があるときです。書くとマージした瞬間に自動クローズされ、確認前に閉じます。代わりに `#<番号>` と参照だけ書き、確認後に手動でクローズします。

手順 2・4 で既定値として決めたことがあれば、「判断したこと」として本文に列挙します。

### 報告して終わる

PR 番号と URL、そして**次に打つコマンド**を報告します。

```
/independent-review <PR番号>
```

ここで終わりです。レビューもマージも worktree の削除もしません。

## 規約はここに写さない

`CLAUDE.md` / `docs/design-notes.md` / `docs/testing.md` / `docs/db-schema.md` の本文を、この SKILL.md に書き写しません。**リンクと「読め」だけを置きます。**

`/independent-review` が同じ方針を取っている理由が、そのまま当てはまります（`docs/git-workflow.md`）。

> **観点リストは `docs/design-notes.md` と `docs/testing.md` が唯一の情報源です。** 約束や規約をエージェント定義側に書き写すと、片方だけが更新されて陳腐化します。

実装スキルは触れる規約の量が最も多いので、写すと最も速く陳腐化します。ここに書くのは、**それらの文書に無いもの** — 手順の順序と、止まる条件だけです。
