ユーザーの言葉をそのまま仕様書として扱わず、会話とリポジトリから意図を補って、実装時に役立つ最小限の issue にします。

## 基本方針

- issue は実装の許可証ではなく、バックログと仕様判断の記録に使う
- 日本語の上手さや、整理された依頼文をユーザーに要求しない
- 調べれば分かることは先に調べる。質問は、答えによって利用者から見える完成結果が変わる点に限る
- 毎回、実装箇所・全エッジケース・テストコードまで先に確定しない
- 独立レビューや全テストは issue 作成の必須工程にしない

運用基準と本文の形は `docs/issue-writing.md` を参照します。

## 1. 意図をつかむ

最初に、依頼を次の観点で短く言い換えます。

- 何に困っている、または何を良くしたいのか
- 変更後に利用者から見てどうなればよいか
- 今すぐ実装する話か、後で扱うバックログか

言い換えに多少の推測が入っても、容易に修正できる内容なら作業を進めます。ユーザーへ文章の書き直しを求めません。

## 2. 必要な分だけ調べる

通常は次だけを短く確認します。

- 関係しそうな既存コード
- open な issue のタイトルとの明らかな重複
- 変更を制約する既存ルール

ファイル・行番号や実測値は、問題の説明に本当に必要な場合だけ issue に載せます。調査のために実装を壊したり、全テストを実行したりしません。

DB スキーマ変更、既存データの変換、金額計算、データ消失、プライバシーに関わる場合だけ、移行方法・失敗時の扱い・必要なテストまで詳しく調べます。

## 3. 必要なら確認する

次の場合だけ、短い質問をまとめて聞きます。

- 複数の解釈があり、選択によって利用者から見える挙動が変わる
- データを削除・変換する可能性がある
- 対象範囲の違いで作業量が大きく変わる
- リポジトリから判断できない好みや優先順位がある

質問するときは、理解した内容と推奨案を先に示します。重要でない文言、内部構造、実装手段は妥当な案を選んで進めます。

## 4. issue を書く

通常は次の3節だけを使います。

```markdown
## やりたいこと

現在の困りごとと、変更後にどうなってほしいか。

## 完了条件

- [ ] 利用者または開発者から見て判定できる条件

## 補足

実装に必要な注意、今回は扱わないこと、関連issueなど。無ければ節ごと省略する。
```

- タイトルは変更後の状態が分かる短い文にする
- `補足` は不要なら削除する
- テスト、対象外、関連、実装案などの見出しは、情報があるときだけ追加する
- `flutter test` 全件成功のような一般的な開発条件を、すべての issue に書き写さない
- 高リスク変更では、データ移行と回帰テストを完了条件に含める

## 5. 作成または提示する

- ユーザーが「issue にして」「作って」「起票して」と明示している場合は、内容がまとまり次第 `gh issue create` で作成する。作成直前の再承認は求めない
- 「issue の形に整理したい」「案を見たい」という依頼なら、本文案を提示するだけで作成しない
- 重要な仕様判断が未解決なら、明示的な作成依頼があっても質問への回答を待つ
- 作成後は URL と、補った重要な前提があればそれだけを報告する

ラベルを付ける場合は、リポジトリに実在するラベルだけを使います。
