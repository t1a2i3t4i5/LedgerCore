要望を **実装着手できる粒度の issue** にします。**書いて提示するところまでで、承認なしに `gh issue create` を実行しません。**

要望: `$request`

## 現在の状況

- ブランチ: !`git branch --show-current`
- open な issue: !`gh issue list --state open --limit 20 --json number,title -q '.[] | "#\(.number) \(.title)"' || echo "（取得できず）"`

## 0. 先に読むもの

`docs/issue-writing.md` を**必ず読みます**（節ごとの理由と実例がここにしかない）。加えて、要望が触れる領域に応じて `docs/design-notes.md` / `docs/testing.md` / `docs/db-schema.md` を読みます。

**このスキルは `gh issue` / `gh pr view` を読みます。** `/independent-review` はこれらを禁じていますが、あれは「既存の指摘に引きずられない」ためのもので、目的が逆です。ここでは重複と過去の見送り経緯の検出が要るので、必ず読みます。

## 1. 要望を分解する

要望を次の形に置き直します。ここで**書けない欄が出たら、それが調査対象か質問対象**です。

- 誰の、どの操作が、いまどう困っているか
- それが**今**問題になった理由（何が前提を壊したか）
- 変えたい振る舞い（before → after）
- 触りそうな既存ファイル

### 大きすぎないか判定する

次のうち **2 つ以上**に当たるなら、起案の前に分割案を提示して合意を取ります。

- `schemaVersion` を上げる
- 新規ディレクトリ + 4 ファイル以上
- 受け入れ条件が 8 個を超える
- UI 変更とデータ層変更の両方を含む
- 「A が無いと B が書けない」依存が 2 段以上

分割は**縦切り**にします。「データ層 issue → UI issue」ではなく「最小で動く 1 本 → 拡張」。前者は片方だけマージしても何も動かず、受け入れ条件が書けません。分割したら、後続の issue には「関連」に切り出し元と**なぜ今回やらないか**を書きます。

## 2. 調査する（質問より先）

**調べれば分かることをユーザーに聞かないこと。** 4 方向を埋めます。

| 方向 | 何を得るか |
| --- | --- |
| 既存実装 | `grep -rn` で対象ファイルと**行番号**。再利用できる既存の口（メソッド・Provider・ウィジェット） |
| 既存 issue / PR | 重複していないか。**過去に入れて外した経緯が無いか**（例: カテゴリ別グラフは #14 で入れ #66 で削除。同じ提案を再び書かないため） |
| 設計上の約束 | `docs/design-notes.md` のうち今回触れるもの。破る必要があるなら、それは質問対象 |
| 実測 | 「〜が無い / 効いていない」は必ず実行結果で示す。`grep -c` の件数、`wc`、**実装を壊して `flutter test` が通ること** |

実測は「事象」節に貼る形（コマンド → 結果）で控えておきます。壊して確かめたら**必ず元に戻し**、`git status` が調査開始時と一致することを確認します。

再利用できる既存の口が見つかったら、**新規に作らない方針を issue に明記**します（#74 が `getTransactionsByRange` を使い回すと書いているのと同じ形）。新機能のために既存を大きく作り替える案は出しません。

## 3. 質問する

調査で埋まらなかった穴だけを、**`AskUserQuestion` で 1 回にまとめて**（最大 4 問）聞きます。1 問ずつ往復すると、調査済みの文脈が回答待ちのあいだに古くなります。

**必ず聞く:**

- ユーザーに見える振る舞いの分岐（何を出すか / いつ出すか / どこから辿れるか）
- データを失う・不可逆な操作を含むか
- `schemaVersion` を上げてよいか
- 既存の設計上の約束を破る必要が出たとき
- スコープの上限（「全部」なのか「今回はここまで」なのか）

**推奨を添えて聞く（選択肢が 2〜3 に絞れるもの）:** 各案の**メリット・デメリットと推奨案**を選択肢の説明に書きます。推奨案を先頭に置き、ラベル末尾に `（推奨）` を付けます。

**聞かずに決める:**

- 既存規約から一意に決まるもの（命名、配置、`formatYen()`、半開区間 `[月初, 翌月初)`、ブランチ名）
- 一般的な妥当解があるもの（並び順、文言、既定値）
- 調査で答えが出るもの

決めたものは issue 本文に `（既定値。変更する場合はコメントで指示）` と添えます。黙って決めると、実装 AI が確定仕様と読むか仮と読むかで揺れます。

回答を待っているあいだ、起案にも `gh issue create` にも進みません。

## 4. 起案する

`.github/ISSUE_TEMPLATE/issue.md` の **7 節（`##`）を増やさない**。情報量は `###` で足します。節を増やすと #55 で潰した「同じ役割の節が別名で散る」状態が再発します。

```
タイトル                    動詞で終える（「〜を追加する」。体言止めにしない）
## 事象                     実測値と ファイル:行 を添える。「〜が汚い」で終わらせない
## なぜ今これが問題になったか  前からそうだったものを今 issue にするなら必須
## 提案
   ### 追加・変更するファイル   ツリー図
   ### データの流れ            screens → providers → AppDatabase の矢印
   ### 詳細仕様               表で断定（書式・並び順・上限・既定値）
   ### UI/UX                 画面要素と、既存画面のどこに入るか（UI 変更があるときだけ）
   ### データ・状態管理への影響  Provider / schemaVersion / notifyListeners（影響があるときだけ）
   ### エラー・エッジケース     表：条件 → 期待する挙動
   ### 実装上の落とし穴        先回りの警告。着手した人が同じ壁で止まらないように
## 対象外                   変更する / しない を表で名指し。理由の欄が要点
## テスト                   壊し方まで書く
## 受け入れ条件              第三者が ○× を付けられる粒度で
## 関連                     切り出し元と、なぜその PR で対応しなかったか
```

不要な `###` は省きます。**`## 対象外` と `## 受け入れ条件` は必ず残します。**

### 仕様をどこまで固定するか

| 階層 | 対象 | 書き方 |
| --- | --- | --- |
| 固定 | 外部から見える振る舞い、書式、公開する名前、ファイル配置、受け入れ条件、対象外 | 表と diff で断定する |
| 推奨 | 内部の分割単位、Provider の持ち方、ウィジェットの粒度 | 「〜の形にする」＋理由 |
| 委譲 | 変数名、private メソッドの構成、テストの具体コード | **書かない** |

境界は「**それが変わったらユーザーの目に見えるか**」で引きます。固定しすぎると、実装 AI が「issue と違うがこちらが正しい」場面で止まります。

### 既存機能を壊さないための欄

既存コードを変更する issue では、次を「提案」または「実装上の注意事項」に必ず入れます。

- 触る既存ファイルを `ファイル:行` で列挙し、**呼び出し元の件数**を `grep -c` の結果で添える
- 今回関係する `docs/design-notes.md` の約束を転記する
- 既存の振る舞いを変えるなら、**変える前の振る舞いを事実として書き残す**
- 受け入れ条件に「`flutter test` が全件通る」を 1 行入れる

### テスト節

`docs/testing.md` に従い、**実装のどこをどう壊せばそのテストが落ちるか**まで書きます。落ちない書き方のテストを足しても、グリーンが増えるだけで何も守られません。自動テストの対象外なら、手で確認する手順を書きます。

このリポジトリで特に落としやすいもの: ウィジェットテストは 360x690・`kMaxAmount` のケース・`textScaler` を 1 本。月を扱うなら `clock` 注入。ログを触るなら `MemoryLogSink`。

## 5. 自己点検

提示する前に、issue 本文を自分で通し読みして確認します。**× が 1 つでもあれば直してから提示します。**

1. タイトルが動詞で終わっている
2. 「事象」に実測値（コマンドと結果）と `ファイル:行` がある
3. 「前からそうだった」ものなら「なぜ今」が書いてある
4. 提案のファイル配置が既存のディレクトリ構成と矛盾しない
5. 再利用できる既存の口を調べ、新規に作らない方針を書いた
6. 詳細仕様の表に**曖昧語が無い**（「適切に」「必要に応じて」「いい感じに」）
7. エッジケース表に、空・0 件・上限値・異常系がある
8. 「対象外」表の各行に**理由**が書いてある
9. テスト節に壊し方が書いてある
10. 受け入れ条件が第三者に ○× を付けられる（「読みやすくなっている」は ×）
11. 触れる設計上の約束をすべて転記した
12. **推測で書いた仕様が残っていない**（残すなら「既定値」と明記）

`--review` が指定されたときだけ、`Agent` で独立レビュアーを 1 体起動し、issue 本文と観点だけを渡してレビューさせます（こちらの結論や期待する回答は渡さない）。指摘は P0 = このままでは実装できない / P1 = 着手後に手戻りする / P2 = 補足、に分類させ、P0/P1 を反映してから提示します。指定が無ければ起動しません。

## 6. 提示して、承認を得てから作成する

本文をスクラッチパッドに書き出し、**全文をチャットに出して**確認を求めます。差分要約で済ませません。

```
上記の内容で issue を作成してよいですか？（修正があれば指摘してください）
```

承認後に作成します。**非対話の `gh issue create` はテンプレートを読まない**ので、本文は自分で組み立てて `--body-file` で渡します。

```bash
gh issue create --title "<タイトル>" --body-file <スクラッチパッドのパス> --label <ラベル>
```

ラベルはこのリポジトリに実在するものだけ使います（`enhancement` / `documentation`）。該当しなければ付けません。作成後、issue の URL と、推奨するブランチ名（`docs/git-workflow.md` の命名規則）を報告します。

## 後続のスキルへの引き継ぎ

- **実装**: 「実装上の落とし穴」と「実装時の注意事項」が申し送り。ブランチ名を報告に含める
- **テスト**: 「テスト」節の壊し方がそのまま入力
- **レビュー**（`/independent-review`）: 「対象外」表がレビュー範囲を決める。レビューで出た範囲外の指摘は、このスキルに戻して新しい issue にし、「関連」に**なぜその PR で対応しなかったか**を書く
