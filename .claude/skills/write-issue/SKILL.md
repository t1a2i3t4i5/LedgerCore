要望を **実装着手できる粒度の issue** にします。**独立レビューを必ず通し**、**書いて提示するところまでで、承認なしに `gh issue create` を実行しません。**

要望: `$request`

## 処理の流れ

- **0. 先に読むもの** — `docs/issue-writing.md` を必ず読む。要望が触れる領域に応じて `design-notes.md` / `testing.md` / `db-schema.md` も
- **1. 要望を分解する** — 困りごと・変化・before → after に置き直す。**大きすぎるなら、起案の前に分割案を出して合意を取る**
- **2. 調査する** — 既存実装 / 既存 issue・PR / 設計上の約束 / 実測。**質問より先**。`grep` と `gh issue` で埋まることをユーザーに聞かない
- **3. 質問する** — 調査で埋まらなかった穴だけを `AskUserQuestion` で 1 バッチ（最大 4 問）。推奨案を添える。**回答を待つあいだ、起案にも起票にも進まない**
- **4. 起案する** — 既存テンプレートの 7 節に組み立てる。`##` は増やさず `###` で足す。仕様は固定／推奨／委譲で書き分ける
- **5. 自己点検（形式だけ）** — 節の有無など、読まずに判定できるものを 5 項目。中身の質は 6 のレビュアーが見る
- **6. レビューと修正をループする** — `reviewer-issue-facts` と `reviewer-issue-spec` を並列起動 → 重大度を付ける → **レビュアーが返した検証レシピを直列に実測** → 反映。**P0 と P1 が 0 件になるまで回す**（上限 3 周）。省略しない
- **7. 提示して、承認を得てから作成する** — 最終版の全文と、周回数・却下した指摘・未反映の P2 を出す。**承認前に `gh issue create` を実行しない**

## 現在の状況

- ブランチ: !`git branch --show-current`
- open な issue: !`gh issue list --state open --limit 20 --json number,title -q '.[] | "#\(.number) \(.title)"' || echo "（取得できず）"`

## 0. 先に読むもの

`docs/issue-writing.md` を**必ず読みます**（節ごとの理由と実例がここにしかない）。加えて、要望が触れる領域に応じて `docs/design-notes.md` / `docs/testing.md` / `docs/db-schema.md` を読みます。

**このスキルは `gh issue` / `gh pr view` を読みます。** `/independent-review` はこれらを禁じていますが、あれは「既存の指摘に引きずられない」ためのもので、目的が逆です。ここでは重複と過去の見送り経緯の検出が要るので、必ず読みます。

## 1. 要望を分解する

要望を次の形に置き直します。ここで**書けない欄が出たら、それが調査対象か質問対象**です。

- 誰の、どの操作が、いまどう困っているか
- それが**今**問題になった理由（何が前提を壊したか）
- 変えたい振る舞い（before → after）
- 触りそうな既存ファイル

### 大きすぎないか判定する

次のうち **2 つ以上**に当たるなら、起案の前に分割案を提示して合意を取ります。

- `schemaVersion` を上げる
- 新規ディレクトリ + 4 ファイル以上
- 受け入れ条件が 8 個を超える
- UI 変更とデータ層変更の両方を含む
- 「A が無いと B が書けない」依存が 2 段以上

分割は**縦切り**にします。「データ層 issue → UI issue」ではなく「最小で動く 1 本 → 拡張」。前者は片方だけマージしても何も動かず、受け入れ条件が書けません。分割したら、後続の issue には「関連」に切り出し元と**なぜ今回やらないか**を書きます。

## 2. 調査する（質問より先）

**調べれば分かることをユーザーに聞かないこと。** 4 方向を埋めます。

| 方向            | 何を得るか                                                                                                                       |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 既存実装        | `grep -rn` で対象ファイルと**行番号**。再利用できる既存の口（メソッド・Provider・ウィジェット）                                  |
| 既存 issue / PR | 重複していないか。**過去に入れて外した経緯が無いか**（例: カテゴリ別グラフは #14 で入れ #66 で削除。同じ提案を再び書かないため） |
| 設計上の約束    | `docs/design-notes.md` のうち今回触れるもの。破る必要があるなら、それは質問対象                                                  |
| 実測            | 「〜が無い / 効いていない」は必ず実行結果で示す。`grep -c` の件数、`wc`、**実装を壊して `flutter test` が通ること**              |

実測は「事象」節に貼る形（コマンド → 結果）で控えておきます。

**壊して確かめたら必ず元に戻します。** 戻し方は「壊す前の内容を控えておき、`Edit` で書き戻す」。最後に `git status` が調査開始時と一致することを確認します。

> **`git checkout -- <file>` を使わないこと。** ユーザーが編集中の未コミット変更ごと HEAD の内容に戻り、**復元できません**。`git status` の一致チェックは、消えたことを事後に検出できるだけです。退避が要るなら `git stash push -- <file>` を使い、実測後に `git stash pop` で必ず戻します（`/independent-review` が同じ罠で置いている警告と同じ）。

再利用できる既存の口が見つかったら、**新規に作らない方針を issue に明記**します（#74 が `getTransactionsByRange` を使い回すと書いているのと同じ形）。新機能のために既存を大きく作り替える案は出しません。

## 3. 質問する

調査で埋まらなかった穴だけを、**`AskUserQuestion` で 1 回にまとめて**（最大 4 問）聞きます。1 問ずつ往復すると、調査済みの文脈が回答待ちのあいだに古くなります。

**必ず聞く:**

- ユーザーに見える振る舞いの分岐（何を出すか / いつ出すか / どこから辿れるか）
- データを失う・不可逆な操作を含むか
- `schemaVersion` を上げてよいか
- 既存の設計上の約束を破る必要が出たとき
- スコープの上限（「全部」なのか「今回はここまで」なのか）

**推奨を添えて聞く（選択肢が 2〜3 に絞れるもの）:** 各案の**メリット・デメリットと推奨案**を選択肢の説明に書きます。推奨案を先頭に置き、ラベル末尾に `（推奨）` を付けます。

**聞かずに決める:**

- 既存規約から一意に決まるもの（命名、配置、`formatYen()`、半開区間 `[月初, 翌月初)`、ブランチ名）
- 一般的な妥当解があるもの（並び順、文言、既定値）
- 調査で答えが出るもの

決めたものは issue 本文に `（既定値。変更する場合はコメントで指示）` と添えます。黙って決めると、実装 AI が確定仕様と読むか仮と読むかで揺れます。

回答を待っているあいだ、起案にも `gh issue create` にも進みません。

## 4. 起案する

`.github/ISSUE_TEMPLATE/issue.md` の **7 節（`##`）を増やさない**。情報量は `###` で足します。節を増やすと #55 で潰した「同じ役割の節が別名で散る」状態が再発します。

```
タイトル                    動詞で終える（「〜を追加する」。体言止めにしない）
## 事象                     実測値と ファイル:行 を添える。「〜が汚い」で終わらせない
## なぜ今これが問題になったか  前からそうだったものを今 issue にするなら必須
## 提案
   ### 追加・変更するファイル   ツリー図
   ### データの流れ            screens → providers → AppDatabase の矢印
   ### 詳細仕様               表で断定（書式・並び順・上限・既定値）
   ### UI/UX                 画面要素と、既存画面のどこに入るか（UI 変更があるときだけ）
   ### データ・状態管理への影響  Provider / schemaVersion / notifyListeners（影響があるときだけ）
   ### エラー・エッジケース     表：条件 → 期待する挙動
   ### 実装上の落とし穴        先回りの警告。着手した人が同じ壁で止まらないように
## 対象外                   変更する / しない を表で名指し。理由の欄が要点
## テスト                   壊し方まで書く
## 受け入れ条件              第三者が ○× を付けられる粒度で
## 関連                     切り出し元と、なぜその PR で対応しなかったか
```

不要な `###` は省きます。**`## 対象外` と `## 受け入れ条件` は必ず残します。**

### 仕様をどこまで固定するか

| 階層 | 対象                                                                           | 書き方                 |
| ---- | ------------------------------------------------------------------------------ | ---------------------- |
| 固定 | 外部から見える振る舞い、書式、公開する名前、ファイル配置、受け入れ条件、対象外 | 表と diff で断定する   |
| 推奨 | 内部の分割単位、Provider の持ち方、ウィジェットの粒度                          | 「〜の形にする」＋理由 |
| 委譲 | 変数名、private メソッドの構成、テストの具体コード                             | **書かない**           |

境界は「**それが変わったらユーザーの目に見えるか**」で引きます。固定しすぎると、実装 AI が「issue と違うがこちらが正しい」場面で止まります。

### 既存機能を壊さないための欄

既存コードを変更する issue では、次を「提案」または「実装上の注意事項」に必ず入れます。

- 触る既存ファイルを `ファイル:行` で列挙し、**呼び出し元の件数**を `grep -c` の結果で添える
- 今回関係する `docs/design-notes.md` の約束を転記する
- 既存の振る舞いを変えるなら、**変える前の振る舞いを事実として書き残す**
- 受け入れ条件に「`flutter test` が全件通る」を 1 行入れる

### テスト節

`docs/testing.md` に従い、**実装のどこをどう壊せばそのテストが落ちるか**まで書きます。落ちない書き方のテストを足しても、グリーンが増えるだけで何も守られません。自動テストの対象外なら、手で確認する手順を書きます。

## 5. 自己点検（形式だけ）

レビューに出す前に、**形式だけ**を確認します。**× が 1 つでもあれば直してから出します。**

1. タイトルが動詞で終わっている（体言止めにしていない）
2. `## 対象外` と `## 受け入れ条件` の節がある
3. 「前からそうだった」ものなら `## なぜ今これが問題になったか` がある
4. 触れる設計上の約束をすべて転記した
5. 推測で決めた仕様に「既定値」の印が付いている

**中身の質（曖昧語、抜けた分岐、判定できない受け入れ条件、事実の誤り）はここで点検しません。** それは 2 体の担当で、同じ観点を両方に置くと、片方だけ更新されて食い違います。ここは節の有無のような、読まずに判定できるものだけです。

## 6. レビューと修正をループする

**必ず実行します。省略できません。** issue 案をスクラッチパッドのファイルに書き出してから、**独立コンテキストのレビュアー 2 体**に見せ、**P0 と P1 が 0 件になるまで**「レビュー → 修正 → 再レビュー」を回します。

### 6-1. 2 体を並列で起動する

**1 つのメッセージの中で `Agent` ツールを 2 回呼び出します。** 別々のメッセージに分けると直列化して待ち時間が倍になります。

| subagent_type | 担当 | 見るもの |
| --- | --- | --- |
| `reviewer-issue-facts` | 書かれた事実が正しいか | `ファイル:行`、メソッドの実在、実測値の再現、既存 issue との重複、過去に入れて外した経緯 |
| `reviewer-issue-spec` | 追加の確認なしで着手できるか | 曖昧語、決まっていない値、抜けた分岐、判定できない受け入れ条件、固定しすぎ |

`reviewer-issue-spec` は **`Read` しか持たず、issue 案のファイル以外を読みません**。コードを読むと、issue に書かれていない仕様を頭の中で補ってしまい「これで着手できる」と誤判定するためです。issue 本文だけで詰まるなら、実装担当も同じ場所で詰まります。

渡すのは **issue 案のファイルパスと、何周目かだけ**です。観点は書きません（エージェント定義側にあるので、ここで重ねると二重管理になって陳腐化します）。

```
LedgerCore の issue 案を、あなたの担当観点でレビューしてください。

issue 案: <スクラッチパッドのパス>
周回: <N> 周目
<2 周目以降のみ> 前回あなたが出した指摘と、それに対してこちらが行った修正:
  <指摘の一行要約と、どう直したか。直さなかったものは「却下: 理由」>

定義済みの出力フォーマットで報告してください。
```

こちらの結論・期待する回答・「この指摘を出してほしい」という誘導は渡しません。**1 周目は前回情報が無いので完全に独立**、2 周目以降だけ対応状況を渡します（渡さないと同じ指摘が永久に出続けます）。

2 体とも返るまで次に進みません。

### 6-2. 重大度を付ける

**2 体は重大度を付けずに返してきます。決めるのはこの表だけです。**

| | 基準 |
| --- | --- |
| **P0** | このままでは着手できない、または着手すると誤ったものが出来上がる — 提案の前提となる事実が誤っている / 外から見える振る舞いが決まっていない / 受け入れ条件が判定不能 / 既存の設計上の約束に反する / 既存 issue と重複している |
| **P1** | 着手はできるが途中で手戻りする — エッジケースの抜け、「対象外」が空、テスト節に壊し方が無い、影響範囲の見落とし、固定しすぎ |
| **P2** | 補足。読みやすさ、あると親切な情報 |

同じ欠陥に 2 体が別方向から到達することがあります。**同じ節の同じ原因を指す指摘は 1 件に統合**します。

### 6-3. 検証レシピを直列に実測する

`reviewer-issue-facts` は **`flutter test` を実行しません**（実装を壊して確かめる検証はファイル変更を伴い、レビュアーはファイルを変更しないため）。代わりに**検証レシピ**を返してくるので、**ここで依頼元が実行します**。

- 実測するのは **P0 と P1 のうち、レシピが付いているものだけ**です。P2 は実測しません
- **1 件ずつ順番に実行します。並列にしないこと**（`.dart_tool` の競合で結果が壊れる）
- 壊して確かめたら必ず元に戻します。**戻し方は Phase 2 の警告に従います**
- **再現した** → P0/P1 のまま 6-4 の反映へ
- **再現しなかった** → 6-4 の基準で却下できます。理由と実行結果を記録します

**issue 案に貼った実測値そのものが疑われている場合（「◯◯を削除しても `flutter test` が全件通る」型）、こちらで同じ手順を再実行するのが唯一の判定方法です。** ここを飛ばすと、**誰も再現していない実測値が「レビュー済み」の issue に残ります** — 着手した人が最初に `flutter test` を流した時点で前提が崩れます。

### 6-4. 反映する

- **P0 と P1 は必ず反映**します
- **P2 は反映するかを選びます。** 見送るものは、issue の「関連」に残すか、報告に 1 行で書きます
- 反映のために**新しい仕様判断が要るとき**（レビュアーが指摘した未決事項を、こちらが決められないとき）は、Phase 3 に戻って `AskUserQuestion` で聞きます。推測で埋めません

**却下できるのは、6-3 の実測で指摘が事実誤認だと示せたときだけです。** その場合も黙って消さず、「却下した指摘」として理由と実行したコマンドを最終報告に残します。もっともらしいが誤った指摘は必ず混ざるので、記録が無いと同じ誤指摘が次回も再発します。**「重要ではないと思ったから」は却下の理由になりません** — それは P2 への引き下げであって、却下ではありません。

反映したら、**何を直したかを 1 行ずつチャットに出します**（全文の再掲は最終版だけで足ります）。

### 6-5. 終了条件と打ち切り

- **P0 と P1 が 0 件になったら終了**します。P2 の未反映分があれば報告に残します
- **上限は 3 周**です

3 周してもなお P0/P1 が残る場合、issue 案に押し込むのをやめて **`AskUserQuestion` でユーザーの判断を仰ぎます**。残った指摘と、なぜ解消できないかを添えます。

途中で次のどちらかに当たったら、3 周を待たずに止めてユーザーに聞きます。

- **同じ指摘が 2 周続けて P0 で出る。** こちらは反映したつもりなので、直し方の解釈が食い違っています。回り続けても収束しません
- **周回ごとに P0/P1 の件数が減らない、または増える。** 直すたびに新しい穴が開く状態で、多くの場合 **issue が大きすぎるサイン**です。Phase 1 の分割判定に戻し、縦切りで 2 本に割る案を提示します

## 7. 提示して、承認を得てから作成する

**最終版の全文をチャットに出して**確認を求めます。差分要約で済ませません。次の 3 つを本文の後ろに添えます。

- **何周回したか**と、各周で P0/P1 が何件から何件に減ったか
- **却下した指摘**（あれば）— 理由と、事実誤認だと示した実行結果
- **反映しなかった P2**（あれば）— 1 行ずつ

```
上記の内容で issue を作成してよいですか？（修正があれば指摘してください）
```

承認後に作成します。**非対話の `gh issue create` はテンプレートを読まない**ので、本文は自分で組み立てて `--body-file` で渡します。

```bash
gh issue create --title "<タイトル>" --body-file <スクラッチパッドのパス> --label <ラベル>
```

ラベルはこのリポジトリに実在するものだけ使います（`enhancement` / `documentation`）。該当しなければ付けません。作成後、issue の URL と、推奨するブランチ名（`docs/git-workflow.md` の命名規則）を報告します。

## 後続のスキルへの引き継ぎ

- **実装**: 「実装上の落とし穴」と「実装時の注意事項」が申し送り。ブランチ名を報告に含める
- **テスト**: 「テスト」節の壊し方がそのまま入力
- **レビュー**（`/independent-review`）: 「対象外」表がレビュー範囲を決める。レビューで出た範囲外の指摘は、このスキルに戻して新しい issue にし、「関連」に**なぜその PR で対応しなかったか**を書く
