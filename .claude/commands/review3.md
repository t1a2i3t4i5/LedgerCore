観点を分けた 3 人の独立レビュアーで、コード差分をレビューします。

## 現在の状況

- ブランチ: !`git branch --show-current`
- 作業ツリー: !`git status --short || echo "（クリーン）"`
- main からの変更ファイル: !`git diff --stat main...HEAD | tail -20 || echo "（なし）"`

## 1. 対象を判定する

引数: `$pr`

- **`$pr` が空** → **作業差分モード**。対象は `main...HEAD`（3 点表記。main 側の進行を混ぜないため）と、未コミットの変更 `git diff HEAD` の両方
- **`$pr` が数値** → **PR モード**。対象は `gh pr diff $pr`

どちらのモードで動いているかを最初に 1 行で宣言してから進めること。

作業差分モードで `main...HEAD` が空かつ作業ツリーもクリーンなら、レビューする対象がないので、その旨を伝えて終了する（3 体を無駄に起動しない）。

## 2. アンカリング防止（あなた自身にも適用される）

このレビューの間、**あなたも次を実行してはいけません**。

| コマンド | いつまで禁止か | 止めるもの |
| --- | --- | --- |
| `gh pr view` / `gh pr checks` / `gh api` / `gh browse` | レビュー中ずっと（PR コメントは最後まで読まない） | 権限（`allowed-tools` に無いので確認が出る） |
| `gh pr comment` | 手順 7 に入るまで | この文章だけ |
| `gh issue create` / `gh issue close` / `gh issue comment` | 手順 6 に入るまで | この文章だけ |
| `gh issue list` / `gh issue view` | **手順 4-3 に入るまで** | この文章だけ |

PR の既存コメント・レビュー・issue を読むと、それを 3 人の報告の答え合わせに使ってしまい、「まだ誰も指摘していない欠陥」を落とします。この体制の価値はそこにあります。

issue だけが手順 4-3 で解禁されるのは、**そこでは 3 人の報告がもう出揃って固定されているから**です。答え合わせに使いようがない状態で、「既に issue にして今回はやらないと決めた指摘」を毎回蒸し返さないためだけに読みます。**手順 4-3 より前に読んではいけません。** 3 体の起動前や統合中に読むと、結局そこへ引きずられます。

**issue から本文やコメントを引き出すオプションを付けてはいけません。** 具体的には `gh issue view` の `--comments`、`gh issue list --json` の `body` / `comments` フィールドです。issue のコメント欄には PR へのリンクや引用が貼られるので、そこから 1 行目の「PR コメントは最後まで読まない」が横から破れます。`allowed-tools` はプレフィックス一致なので、どちらも機械的には止められません（`gh issue list --json number,title,body` が本文を返すことは実測済み）。本文が要るのは 4-3 の突き合わせ対象に絞った `gh issue view <N>` だけです。

**表の右列のとおり、`gh issue` 系と `gh pr comment` を止めているのはこの文章だけです。** `allowed-tools` はコマンド実行全体にかかる粒度しか持たず、「手順 N 以降だけ」という時制を書けません。見た目が同じ表の行でも、担保の強さは違います。

## 3. 3 体を並列で起動する

**1 つのメッセージの中で Agent ツールを 3 回呼び出します。** 別々のメッセージに分けると直列化して待ち時間が 3 倍になります。

| subagent_type | 担当観点 |
| --- | --- |
| `reviewer-correctness` | 正確性（バグ、境界値、null と例外、drift のスキーマとマイグレーション） |
| `reviewer-design` | 設計・保守性（依存の向き、約束との整合、命名、重複、抽象度） |
| `reviewer-tests-docs` | テスト・ドキュメント（回帰テストの有無と実効性、docs の追従） |

渡すプロンプトは **対象と差分取得コマンドだけ** にします。観点の指示は書かないでください（エージェント定義側にあるので、ここで重ねると二重管理になって陳腐化します）。

```
LedgerCore の以下の差分を、あなたの担当観点でレビューしてください。

対象: <作業差分モード: 「ブランチ xxx の main からの差分と未コミット変更」 / PR モード: 「PR #N」>
差分取得コマンド（これを 1 回だけ実行してください。他の差分取得手段は使わないこと）:
  <作業差分モード> git diff main...HEAD  および  git diff HEAD
  <PR モード>      gh pr diff <N>

差分の周辺コードは必要な範囲で Read / Grep してください（探索の範囲と回数の規律はあなたの定義にあります）。
誰が書いたコードか、過去にレビューされたことがあるかの情報は与えません。推測もしないでください。
定義済みの出力フォーマットで報告してください。
```

3 体すべての結果が返るまで、次の手順に進まないこと。

## 4. 集約する

### 4-1. 重複を統合する

観点を分けていても、同じ欠陥に別方向から到達することがあります。

- 「同じファイルの同じ原因」を指す指摘は 1 件に統合する。行番号が違っても原因が同じなら統合する
- 統合したものには **`検出: 3 人中 N 人`** を記録する
- **複数人が独立に同じ欠陥に到達した指摘は、確信度を 1 段上げる。** 過去に `Infinity` の素通りを 3 人全員が独立に指摘した実例がある
- 1 人だけの指摘は、その人の観点固有の見え方である可能性があるので、そのまま採用せず次の検証にかける

### 4-2. 重大度を付け直す

レビュアーが付けた重大度は参考値として扱い、次の基準で統一します（観点が違うと基準がずれるため）。

| 重大度 | 基準 |
| --- | --- |
| 致命 | 保存済みデータの破壊・消失、マイグレーション失敗で DB が中途半端な状態に固定される、起動不能 |
| 重大 | 金額や集計値が誤って表示・保存される、入力バリデーションの穴（`Infinity` / `NaN` / 桁あふれ）、未捕捉例外でのクラッシュ、CLAUDE.md の「設計上の約束」の破壊、修正したバグの回帰テストがない |
| 中 | UI の overflow や可読性の破綻、テストが実質何も保証していない、docs が実装に追従していない |
| 軽微 | 命名、重複、コメント、抽象度 |

**この付け直しを既知の仕分け（4-3）より前に置いているのは、4-3 の除外条件が重大度で分岐するからです。** レビュアー 3 体の重大度表はこの表と一致していません（たとえば `reviewer-correctness` の 中 は「特定条件でのみ起きる軽微な計算ずれ」ですが、この表では「金額や集計値が誤って表示・保存される」は 重大 です）。順序を入れ替えると、上の表なら 重大 になる指摘が、レビュアーの自己申告が 中 だったというだけで既知に落ち、実測もされずに 1 行へ縮みます。

### 4-3. 既に issue になっている指摘を仕分ける

ここで初めて `gh issue list` / `gh issue view` を解禁します（手順 2 の表を参照）。`--comments` は付けません。

同じ PR を 2 回目にレビューすると、修正した指摘は消えますが、**「別 issue に切り出した」指摘は PR 内のコードが変わっていないので必ず再掲されます**。実例として issue #30 は PR #27 と #28 の両方で挙がりました。毎回同じものを実測し直して報告の先頭に並べても、ユーザーは既に「今回はやらない」と判断済みです。

1. `gh issue list --state open --limit 200 --json number,title` で **タイトル一覧だけ** を取る。**200 件に達していたら「一覧が上限に達した」と報告に書きます** — 打ち切りが起きると照合漏れが「既知なし」と区別できなくなります
   - `--state open` なのは意図的です。**closed の issue は見ません** — 修正済みのものが再発したなら、それは既知ではなく回帰なので、新規として実測にかけるべきです。ただし `not planned` で閉じた issue は「やらないと決めた記録」なので、その運用を始めるときはこの行を見直します
2. 統合後の各指摘について、対象ファイルと原因が近そうな issue **だけ** を `gh issue view <N>` で開き、本文と突き合わせる（全件の本文を読み込まない）
3. **同じ欠陥を指していると確認できたものだけ** に `既知: #N` を付ける。タイトルの語が似ているだけで既知にしない。この印は報告時に `K1.` 形式へ変換します（手順 5）
4. **ただし次のどちらかに当たるものは既知にしない。** ここを外すと、この仕組みが欠陥を隠す側に回ります
   - **今回の差分が、その欠陥のあるファイル・行を変更している** — 「その issue をつぶすために立てた PR かどうか」では判定しません（`gh pr view` が禁止されているので PR の題目は読めません）。**差分に現れたファイル・行と、issue が指す箇所が重なるかどうかだけ**で判定します。重なるなら、修正が不完全である可能性がそのまま **PR の主目的の失敗** なので、既知に落とすといちばん見るべきものが 1 行に縮みます
   - **4-2 で付け直した重大度が 致命 か 重大** — issue には軽い形で登録されていても、今回それより重い経路まで辿れたなら本編に残します。issue 側の重大度は、その時点で見えていた範囲の判断でしかありません
5. 判定が微妙なものは既知にせず、新規として次の実測検証にかける。**再掲する方が、見落とすより安全です**

`既知` を付けた指摘は次の実測検証（4-4）の対象から外し、報告では本編ではなく専用セクション（手順 5）に出します。

作業差分モードでも同じことをします。見ているコードは同じなので、issue 化済みの指摘は同じように再掲されます。

`gh` が使えない（未認証・リモート未設定・オフライン）ときは、**全件を新規として 4-4 へ進み、「issue との照合ができなかった」と既知セクション（手順 5）に 1 行書きます。** 黙って飛ばすと、照合した結果 0 件だったのか照合できなかったのかが読み手に区別できません。

### 4-4. 実測で検証する（ここは必ず直列に行う）

4-3 で `既知` を付けなかった指摘について、各レビュアーが書いた「検証レシピ」を、**1 件ずつ順番に** 実行します。**並列実行しないこと**（`.dart_tool` の競合で結果が壊れる）。

- 「テストが何も保証していない」系の指摘は、**実装を実際に壊して `flutter test` が通ることを確かめる**。これが最も確実な判定方法
- 壊して確かめたら **必ず元に戻す**。`git checkout -- <file>` などで復元し、`git status` がレビュー開始時と一致することを確認する
- **再現しなかった指摘は削除せず「却下」として報告に残し、なぜ再現しなかったかを書く。** もっともらしいが誤った指摘は必ず混ざります。黙って消すと同じ誤指摘が次回も再発します
- 検証に時間がかかりすぎる、または破壊的で戻せないものは「未検証」と明記して残す。**却下と未検証は別物です** — 却下は実測して再現しなかったもの、未検証は実測そのものをしていないものです

## 5. 報告する

本編に出すのは **4-4 で却下されなかった指摘** です（既知でも却下でもないもの。実測が破壊的で戻せないなどの理由で「未検証」と付けたものは、本編ではなく専用セクションに出します）。重大度順（致命 → 軽微）に、1 件ずつ **番号を振って** 出します。ユーザーは「3 は別 issue に」のように番号で指示を返してくるので、番号は必須です。

```
## 1. [重大] 一行要約
- 対象: lib/db/database.dart:112-118
- 検出: 3 人中 2 人（正確性・テスト）   確信度: 高
- 事象:
- 再現条件:
- 裏付け: 実測（実行したコマンドと結果を具体値で）
- 推奨対応: **修正** / 別 issue / 仕様確認   ← 推奨を 1 つだけ太字にする
- 理由:
```

全件のあとに次を付けます。

- **既知の指摘（issue 化済み）** — 4-3 で `既知: #N` を付けたもの。`K1. [重大度] 一行要約 — #N` の 1 行ずつ（重大度は 4-2 で付け直した値）。**実測検証はしていない旨を明記する**。番号を `K` 系で振るのは、ユーザーが「K2 はやっぱり今回直す」と番号で指示を返せるようにするため（返ってきたときの扱いは手順 6）。重大度を省かないのは、既知に落ちたものの軽重が読み手に分からなくなるのを防ぐため。0 件なら「なし」と書く（黙って省略しない。省略すると「照合をしなかった」のか「一致が無かった」のか区別できない）。`gh` が使えず照合できなかったときも、ここに 1 行書く
- **却下した指摘** — 4-4 で実測して再現しなかったもの。`R1.` の形で番号を振る（ユーザーが「R2 は再検証して」と返せるように）。指摘内容と、なぜ再現しなかったか
- **未検証の指摘** — 4-4 で実測そのものをしなかったもの（時間がかかりすぎる / 破壊的で戻せない）。`U1. [重大度] 一行要約` の形で番号を振る。**なぜ実測しなかったかを必ず書く**。0 件なら「なし」と書く。**却下と混ぜないこと** — 却下は実測して否定したもので、こちらは判断がついていないものです
- **観点外の気づき** — 3 人の「観点外だが気づいた点」を統合したもの
- **仕分け表** — **本編の新規指摘だけ** を「修正 / 別 issue / 説明」の推奨つきで 1 行ずつ並べた表。ユーザーがこの表に対して番号で指示を返せる形にする。既知の指摘は表に入れない

指摘は推測ではなく **実測で裏付ける**。数値（コントラスト比、overflow の px 数、しきい値の再現条件）があると仕分けが速くなります。

## 6. 修正する場合

ユーザーが「修正して」と指示した項目について:

- **修正前の実装で失敗する回帰テストを先に書き、実際に落ちることを確認してから** 修正する。落ちることを確認していないテストは、通っても何も証明しません
- **`K` 番号（既知）を指定されたら、先に 4-4 の実測検証をしてから修正する。** 既知は実測を飛ばしているので、そのまま直すと「再現するか分からないもの」を直すことになります。実測が通ったらその項目を本編の番号体系に繰り上げ、対応する issue は修正内容へのリンクを添えて閉じます。`R` 番号（却下）を指定されたときも同じく、まず再検証から入ります
- スコープ外（スキーマ変更を伴うなど）は PR を膨らませず別 issue にし、**切り出した理由を issue 本文と PR コメントの両方に書く**（`gh issue create` はここで解禁されます）
- 判断の根拠は PR 本文にも残す。squash merge 運用なので、PR 本文が唯一の要約になります

## 7. PR にコメントを投稿する（PR モードのときだけ）

**投稿前に必ずユーザーに確認を取ります。** PR コメントは公開されて取り消しにくいうえ、**投稿した内容は次回以降の独立レビューにとってアンカリング材料になります**。誤指摘を残すと将来のレビューを汚すので、確認は省略しないこと。

`AskUserQuestion` で「このまま投稿 / 修正して投稿 / 投稿しない」を尋ねてから、次で投稿します。

```bash
gh pr comment $pr --body-file -
```

本文が長く日本語とコードブロックを含むので、`--body` の一行渡しは避けてヒアドキュメントを使います。本文の構成:

```
## 独立 3 レビュー結果（正確性 / 設計・保守性 / テスト・ドキュメント）

観点を分けた 3 つの独立コンテキストでレビューし、指摘を実測で検証したうえで統合した。

### 致命 / 重大 / 中 / 軽微 （該当のあるものだけ）
### 既知（issue 化済み・今回は対応しない）
### 再現しなかった指摘
### 実測できなかった指摘
### 別 issue に切り出したもの（切り出した理由つき）
```

**本編（致命 / 重大 / 中 / 軽微）に投稿するのは、手順 4-4 で却下されなかった指摘だけ** です。残る 3 つは末尾に一行リストで残しますが、**性質が違うので書き分けます**。

| セクション | 何か | 「未検証」と書くか |
| --- | --- | --- |
| 既知 | 4-3 で実測を省いたもの | **書く** |
| 再現しなかった指摘 | 4-4 で実測して再現しなかったもの | **書かない**（実測して否定したという最も価値のある情報が消え、読み手は「まだ調べていない疑い」と受け取る） |
| 実測できなかった指摘 | 4-4 で実測そのものをしなかったもの | **書く**（理由も添える） |

書式は手順 5 と同じです（`K1.` / `R1.` / `U1.`）。ここを長く書くと、次回の独立レビューにとってのアンカリング材料が増えるだけなので 1 行ずつに留めます。どのセクションも 0 件なら「なし」と書き、見出しごと省くことはしません。

作業差分モードのときは投稿しません。
