観点を分けた 3 人の独立レビュアーで、コード差分をレビューします。**報告して終わります** — 修正も PR へのコメント投稿もしません。

## 現在の状況

- ブランチ: !`git branch --show-current`
- 作業ツリー: !`git status --short || echo "（クリーン）"`
- main からの変更ファイル: !`git diff --stat main...HEAD | tail -20 || echo "（なし）"`

## 1. 対象を決める

引数: `$pr`

先頭の `#` を落としてから判定します（`/review3 #35` は PR #35 です）。

- **空** → **作業差分モード**。対象は `main...HEAD`（3 点表記。main 側の進行を混ぜないため）と、未コミットの変更の**両方**。未コミットの変更は `git diff HEAD`（追跡済みファイルの変更）と、`git status --porcelain` が `??` で返す**未追跡ファイル**の 2 つからなる。`git diff` は未追跡ファイルを一切出力しないので、`git diff HEAD` だけでは新規に足したウィジェットやテストが誰の目にも入らない
- **数値** → **PR モード**。対象は `gh pr diff <番号>`

どちらのモードで動いているかを最初に 1 行で宣言します。

作業差分モードで `main...HEAD` が空かつ作業ツリーもクリーンなら、レビューする対象がないので、その旨を伝えて終了します（3 体を無駄に起動しない）。

## 2. レビュー中に読まないもの

**あなたも 3 体も、このコマンドが終わるまで次を実行しません。**

`gh pr view` / `gh pr comment` / `gh pr checks` / `gh issue`（全サブコマンド） / `gh api` / `gh browse`

PR の既存コメント・レビュー・issue を読むと、それを 3 人の報告の答え合わせに使ってしまい、「まだ誰も指摘していない欠陥」を落とします。この体制の価値はそこにあります。

## 3. 3 体を並列で起動する

**1 つのメッセージの中で Agent ツールを 3 回呼び出します。** 別々のメッセージに分けると直列化して待ち時間が 3 倍になります。

| subagent_type | 担当観点 |
| --- | --- |
| `reviewer-correctness` | 正確性（バグ、境界値、null と例外、drift のスキーマとマイグレーション） |
| `reviewer-design` | 設計上の約束（CLAUDE.md の「設計上の約束」に反していないか） |
| `reviewer-tests-docs` | テスト・ドキュメント（回帰テストの有無と実効性、docs の追従） |

渡すプロンプトは **対象と差分取得コマンドだけ** にします。観点の指示は書かないでください（エージェント定義側にあるので、ここで重ねると二重管理になって陳腐化します）。

```
LedgerCore の以下の差分を、あなたの担当観点でレビューしてください。

対象: <作業差分モード: 「ブランチ xxx の main からの差分と未コミット変更」 / PR モード: 「PR #N」>
差分取得コマンド（依頼元が指定したものだけを使い、他の差分取得手段は使わないこと）:
  <作業差分モード> git diff main...HEAD  および  git diff HEAD   ← 2 本とも実行する
                   加えて次の未追跡ファイルも新規追加分としてレビュー対象に含める（Read で全文を読む）:
                     <git status --porcelain の "??" 行から拾ったパスを列挙。無ければ「なし」>
  <PR モード>      gh pr diff <N>

差分の周辺コード・関連ファイルは Read / Grep で必要な範囲だけ読んでください。
誰が書いたコードか、過去にレビューされたことがあるかの情報は与えません。推測もしないでください。
定義済みの出力フォーマットで報告してください。
```

3 体すべての結果が返るまで、次に進まないこと。

## 4. 統合して重大度を付ける

観点を分けていても、同じ欠陥に別方向から到達することがあります。**「同じファイルの同じ原因」を指す指摘は 1 件に統合します。** 行番号が違っても原因が同じなら統合します。

3 体は重大度を付けずに返してきます。**重大度を決めるのはこの表だけです。**

| 重大度 | 基準 |
| --- | --- |
| 致命 | 保存済みデータの破壊・消失、マイグレーション失敗で DB が中途半端な状態に固定される、起動不能 |
| 重大 | 金額や集計値が誤って表示・保存される、入力バリデーションの穴（`Infinity` / `NaN` / 桁あふれ）、未捕捉例外でのクラッシュ、CLAUDE.md の「設計上の約束」の破壊、修正したバグの回帰テストがない |
| 中 | UI の overflow や可読性の破綻、テストが実質何も保証していない、docs が実装に追従していない |
| 軽微 | 上のどれにも当たらないが、実害を具体的に説明できるもの |

**[致命] と [重大] はブロッカーです。** **実測できたかどうかによらず**ブロッカー欄に置きます。この対応をここで固定しておかないと、実測が権限や環境の都合で止まった回に重い指摘がまとめて「それ以外の指摘」の 1 行へ沈み、ブロッカー 0 件として「マージして問題ない」が出力されます。**例外は 1 つだけで、実測して再現しなかったものは「再現しなかった指摘」へ移ります**（実測できなかったものとは別扱い）。[中] と [軽微] はブロッカーに置きません。

## 5. ブロッカーだけ実測で検証する

**実測するのは [致命] と [重大] だけです。** [中] と [軽微] は実測せず、レビュアーの記述のまま 1 行で報告します。実測は直列にしか行えず時間がかかるので、マージを止める判断に効くものだけに使います。

各レビュアーが書いた「検証レシピ」を、**1 件ずつ順番に** 実行します。**並列実行しないこと**（`.dart_tool` の競合で結果が壊れる）。

- 「テストが何も保証していない」系の指摘は、**実装を実際に壊して `flutter test` が通ることを確かめる**。これが最も確実な判定方法
- 壊して確かめたら **必ず元に戻す**。復元は「壊す前の内容を控えておき、Edit で書き戻す」で行い、`git status` がレビュー開始時と一致することを確認する
- **作業差分モードで `git checkout -- <file>` を使わないこと。** このモードでは未コミットの変更そのものがレビュー対象なので、HEAD の内容に戻すと壊した部分だけでなく**レビュー対象の未コミット変更ごと消える**。退避が必要なら `git stash push -- <file>` を使い、実測後に `git stash pop` で必ず戻す

実測の結果で行き先が決まります。

- **再現した** → ブロッカー欄に、実行したコマンドと結果（具体値）を添えて置く
- **再現しなかった** → 削除せず「再現しなかった指摘」へ移し、なぜ再現しなかったかを添える。もっともらしいが誤った指摘は必ず混ざります。黙って消すと同じ誤指摘が次回も再発します
- **実測できなかった**（破壊的で戻せない・時間がかかりすぎる・環境が足りない） → ブロッカー欄に残し、`実測できず: 理由` を添える

数値（コントラスト比、overflow の px 数、しきい値の再現条件）があると判断が速くなります。

## 6. 報告する

重大度順に、全体で**通し番号を 1 本**振ります。ユーザーは「4 も直して」のように番号で指示を返すので、番号は必須です。「再現しなかった指摘」は却下されたもので重大度を持たないため、重大度順に並べたあとの**末尾**に続けて番号を振ります。

```
## ブロッカー — 直さずにマージすべきでないもの

### 1. [重大] 一行要約
- 対象: lib/db/database.dart:112-118
- 何が壊れるか: 具体的な入力値・操作手順で
- 実測: 実行したコマンドと結果（具体値）。実測できなかった場合は `実測できず: 理由`
- 直し方: 一行で

（ブロッカーが 0 件のときだけ「なし。このままマージして問題ない」と書く）

## それ以外の指摘

4. [中] 一行要約 — lib/screens/xxx.dart:88
5. [軽微] 一行要約 — test/xxx_test.dart:20

## 再現しなかった指摘

7. 一行要約 — 実測した結果どうだったか、なぜ再現しなかったか
```

「それ以外の指摘」と「再現しなかった指摘」は 1 行ずつに留めます。ブロッカーでないものを詳しく書くと、読み手がもう一度仕分けをすることになります。
